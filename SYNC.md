# Синхронизация и хранение данных

Рабочая спецификация. Затрагивает два репозитория: `RedCalendar-Female` (iOS) и `redcalendar-api` (Node/Postgres).

Локальная база (GRDB) остаётся источником правды для работы офлайн. Сервер раздаёт изменения по монотонному счётчику ревизий. Один эндпоинт, одна новая колонка на таблицу.

---

## 1. Решения

| # | Вопрос | Решение |
|---|---|---|
| 1 | Курсор | Монотонный счётчик ревизий на пользователя, не метка времени |
| 2 | Грязные строки | Отдельная колонка `dirty_seq`; `updated_at` уходит из моделей |
| 3 | Эндпоинт | Один: `POST /data/sync`, push и pull в одном запросе |
| 4 | Профиль | Синхронизируется целиком, живёт в локальной таблице |
| 5 | Отвергнутая строка | Сервер побеждает молча |
| 6 | Logout | Локальная база стирается; выходим сразу, несохранённое не досылаем |
| 7 | Удаление | Всегда tombstone; физического удаления в доменном коде не остаётся |
| 8 | Личность в профиле | `phone_number` и `email` пишет только сервер |
| 9 | Индикатор | `.navigationBarLeading`, парный к меню настроек |
| 10 | Владение стором | `AppStore.shared`, старт в `didFinishLaunchingWithOptions` |
| 11 | Телефон | Вход только для v2.0, регистрации нет; поиск номера переезжает из Firebase в Postgres |
| 12 | Состояние устройства | Пояс (IANA) и `last_seen_at` пишутся на каждом `/data/sync` |
| 13 | Выделения | Своя таблица по дню, как комментарии; удаление цикла их не уносит |
| 14 | Снимок для pull | Строка пользователя блокируется на **каждом** прогоне, включая pull-only (§4.3) |
| 15 | Граница страницы | `next_cursor` — минимум по усечённым таблицам, не максимум по строкам (§4.4) |
| 16 | Владелец базы | Сверяется **при входе**, до первого push; первый прогон установки — pull-only (§5.1, §6) |
| 17 | Эволюция схемы | `full_resync_required` зарезервирован в ответе с первого дня (§4.6) |

### 2.4. Найденные дефекты

Все проверены по коду, все существуют на момент написания.

**D1. `updatedAt = nil` означает две разные вещи.**
`DatabaseMiddleware.swift:230` выбирает между мягким и физическим удалением по `existing.updatedAt != nil`. Но `handleSetFlowLevel:306`, `handleMarkPeriodEnd:274` и `handleUnmarkPeriodEnd:288` тоже ставят `updatedAt = nil`. Сценарий: создали цикл → синхронизировали → поменяли уровень выделений → сняли отметку начала → **физическое удаление**, сервер об удалении не узнаёт, следующий pull воскрешает цикл.
Сегодня ветка мягкого удаления **мертва**: значение в `updated_at` не пишет никто, поэтому условие всегда ложно и снятие отметки всегда физическое. Практическое следствие — не для сервера, а для импорта: локально удалённый цикл не оставил надгробия, и §10 воскресит его (см. §10.4).
Закрывается решениями 2 и 7. **Закрыто в пункте 5** — `dirty_seq` заменил `updated_at`, `deleteCycle` ушёл из протокола, снятие отметки начала всегда пишет надгробие.

**D2. Настройки цикла всегда дефолтные после холодного запуска.**
`AppReducer.swift:195` читает `state.currentUser?.settings?.cycle`. `currentUser` живёт в `authState.authenticated(userDetails:)`, а `AuthMiddleware.swift:25` на холодном запуске диспатчит `userDetails: nil`. Метода «получить данные пользователя» нет — восстановить некому.
Итог: длина цикла, длина месячных и лютеиновая фаза всегда 28/5/14. У третьего тестового пользователя реально 26/6/14, и она активна — весь её прогноз построен на чужих числах.
Закрывается решением 4. **Закрыто в пунктах 6 и 8** — профиль наблюдается из `user_profile`, а заполняет его синхронизация.

**D3. Фоновый пуш не будет работать.**
`RedCalendar_FemaleApp.swift:38-39`: `appDelegate.appStore = store` и стартовые экшены сидят в `.onAppear`. Фоновый пуш запускает приложение **без сцены** — замыкание `WindowGroup` не выполняется, `@StateObject` (autoclosure) не вычисляется, стора нет, `appStore` остаётся `nil`, `.auth(.check)` не диспатчится. Следствие: `fetchCompletionHandler` не получает полезного результата, iOS начинает душить фоновые пуши.
Закрывается решением 10. **Закрыто в пункте 10** — `AppStore.shared`, `didFinishLaunchingWithOptions`, `didReceiveRemoteNotification` есть и проверены на устройстве (§8.1).

**D4. Logout при сетевой ошибке не выходит.**
`AuthMiddleware.swift:220-234`: при ошибке, отличной от 401, только `AppLogger.error` — `.notAuthenticated` не диспатчится, пользователь остаётся залогиненным. С решением 6 это становится опасным: wipe может сработать при живой сессии.
**Закрыто в пункте 9** — `.logout` доходит до `.notAuthenticated` при любом исходе сетевого запроса.

**D5. Первый вход по телефону сломан.**
`female.js:72` — `createFemale` деструктурирует только `{ email, name, settings }`; переданные `id` и `phone_number` теряются, id генерируется заново.
`verify-flash-call.js:170` передаёт `{ id: firebaseUID, ... }`, затем `authService.createDevice(firebaseUID, ...)` ищет пользователя по `firebaseUID` — не находит → `500 DEVICE_CREATION_FAILED`, в базе остаётся строка со случайным id. Строки накапливаются: `email` у них `NULL`, а `NULL` не нарушает `UNIQUE`.
`verify-code.js:185` делает правильно: не передаёт `id`, читает сгенерированный обратно.
Достижимо для любого телефонного пользователя, которого нет в Postgres — то есть для переустановивших приложение. Обновившиеся поверх старого идут через `/auth/migrate`, где `migrateUser` вставляет id правильно.
Закрывается §11.3: создание переезжает в `check-phone` до звонка, ветка в `verify-flash-call` удаляется, а `createFemale` начинает уважать переданный `id`.
**Закрыто в пункте 4** — `createFemale` уважает переданный `id`, так что `verify-flash-call.js:202-225` создаёт строку с правильным ключом, и последующий `createDevice(firebaseUID, ...)` находит её; `23505` разбирается по `error.constraint`. Сама ветка создания в `verify-flash-call` при этом ещё на месте — её перенос в `check-phone` до звонка (§11.3) остаётся частью пункта 15, но это перестройка архитектуры на будущее, а не остаток этого дефекта: симптом (500, строки-сироты с `NULL` в `email`) не воспроизводится.

**D6. `GET /auth/verify` сломан и не используется.**
`verify.js` возвращает `result.user_id`, `result.email`, `result.name`, а `authService.verifyDevice` отдаёт `{ data: { device, user } }` — все три `undefined`. iOS-модель `VerificationResponse` ждёт обязательный `last_visit_at`, которого нет вообще. Метод не вызывается ни с одной стороны.
Замещается проверкой владельца при входе (§6) и в ответе `/data/sync` (§5.1, шаг 5). **Сам сервис `verifyDevice` исправен и переиспользуется** — сломан только слой эндпоинта. Эндпоинт, его маршрут в `api/auth.js`, метод `APIServiceProtocol.verifyDevice` и модель `VerificationResponse` удаляются (§12, п. 11).
**Закрыто в пункте 11** — с обеих сторон: `APIServiceProtocol.verifyDevice`/`VerificationResponse` удалены из `APIService.swift`, маршрут `/auth/verify` и `app/api/auth/verify.js` удалены с сервера; `authService.verifyDevice` остался и используется `/data/sync`.

**D7. `POST /push/send` без авторизации.**
`api/push.js` принимает `user_id` в теле и не проверяет ничего. Кто угодно шлёт пуш кому угодно.
**Закрыто в пункте 11 — удалением, а не защитой.** У эндпоинта не нашлось ни одного вызывающего; `app/api/push.js` удалён целиком, `sendAlertToUser` остался в `services/push.js` как точка входа для будущего планировщика уведомлений (§15).

**D8. Push умеет только alert, и не умеет адресовать.**
`push.js:198-199` — `apns-push-type: alert`, `apns-priority: 10`, захардкожено в `sendToEndpoint`, а не в `sendToUser`. Silent push требует `background` и priority 5; priority 10 с background-типом APNs отвергнет.
Вторая половина: `getUserTokensByEnvironment(userId)` (`push.js:78`) выбирает только `apns_token`. Исключить вызвавшее устройство (§7) нечем — `device_id` в выборке нет.
**Закрыто в пункте 11** — `getUserTokensByEnvironment(userId, { excludeDeviceId })` выбирает и `device_id`; `sendToUser` расщеплён на `sendAlertToUser` (`alert`/10, старое поведение) и `sendSyncToUser` (`background`/5, `apns-collapse-id: sync`); `sendToEndpoint` параметризован `pushType`/`priority`/`collapseId` вместо хардкода.

**D9. Клиент не различает коды ошибок HTTP.**
`APIService.swift:470-489`: всё `>= 400` с разбираемым телом схлопывается в `.serverError(String)`, а сервер **всегда** отдаёт разбираемый конверт `{error, message, timestamp}`. Ветка `.httpError(Int)` практически недостижима. Таблица §5.6 (429 по `Retry-After`, backoff на 5xx, `.failed` на прочих 4xx) в таком виде нереализуема.
Закрывается §5.6. **Закрыто в пункте 7** — `validateHTTPResponse` различает 429 (с `Retry-After`) и 5xx до общей ветки `>= 400`; `.serverError`/`.httpError` не тронуты.

**D10. На сервере нечем применить DDL.**
`README.md` утверждает «Таблицы создаются автоматически при первом запуске приложения» — такого кода нет ни в одном файле. Значит форма таблиц `cycles`/`comments`/`user_tags`/`day_tags`, если они существуют, никем не проверена и не зафиксирована.
Закрывается §3.5 и §12, п. 1. **Закрыто в пункте 1** — `scripts/inspect_schema.js` (снимок), `app/migrations/*.sql` + `scripts/migrate.js` (раннер, `schema_migrations`); README поправлен.

## 3. Модель данных

### 3.1. Локально — миграция v3

```
cycles / comments / user_tags / day_tags / flow_levels
  + dirty_seq  INTEGER          -- NULL = чисто; иначе поколение локальной правки

flow_levels (НОВАЯ)
  day_number INTEGER PRIMARY KEY
  level      INTEGER            -- NULL = tombstone, как comment
  dirty_seq  INTEGER

user_profile (id = 1)
  user_id TEXT
  name TEXT, email TEXT, phone_number TEXT
  settings_json TEXT
  dirty_seq INTEGER

sync_state (id = 1)
  user_id       TEXT             -- владелец базы; NULL = ещё не установлен
  cursor        INTEGER NOT NULL DEFAULT 0
  local_seq     INTEGER NOT NULL DEFAULT 0
  import_status TEXT
  known_tables  TEXT NOT NULL    -- JSON-массив имён таблиц, которые понимает эта сборка (§4.6)
```

Бэкфилл: все существующие строки → `dirty_seq = 1`, `local_seq = 1`, `user_id = NULL`, `known_tables` — текущий набор этой сборки (§4.6: на обновлении он не должен выглядеть выросшим, иначе первый же запуск закажет полный ресинк впустую). Словари `cycles.flow_levels` раскладываются в строки `flow_levels`, тоже с `dirty_seq = 1`.

**`known_tables` пишется литералом, а не из константы кода.** По той же причине, что и раскладка ниже, но с более дорогой ошибкой: константа растёт вместе со сборкой, а в строке должно остаться то, что понимала сборка, выполнившая миграцию. Иначе сравнение §4.6 — «в коде шире, чем в строке» — не сработает никогда, и добавленная шестая таблица потеряется молча. Имена — ключи `changes` (§4.1), профиль в их числе: для курсора он такой же поток, как таблица (§4.4).

**Строку заводит только `sync_state`.** `local_seq` нужен с первой же локальной записи, а `user_profile` до пункта 8 некому заполнить: её единственную строку пишет синхронизация. Пустой таблицы и отсутствующей строки читателю достаточно — профиля нет.

**Раскладка делается сырым SQL**, а не через `CycleRecord`. Миграция, однажды выполнившаяся на чьём-то устройстве, не имеет права поменять смысл, а структура-модель меняется — та же причина, по которой `v2_tag_category_not_null` подставляет литеральный `0`, а не `TagCategory.fallback.rawValue`. Читать JSON надо через `json_each(flow_levels)`.

`updated_at` и `flow_levels` убираются из Swift-структур, **колонки остаются на месте**. `updated_at` везде `NULL` — проверено: ни одна ветка `DatabaseMiddleware` никогда не записывала туда значение; `cycles.flow_levels` объявлена `NOT NULL DEFAULT '{}'`, так что вставка без неё берёт дефолт, и после раскладки её не читает никто. GRDB пишет только поля структуры, так что мёртвые колонки ничего не стоят и не требуют перестроения таблиц.

Вместе с `updated_at` из `DatabaseServiceProtocol` уходит `lastSyncTimestamp()` — единственный её читатель (см. §13, «Курсор как `MAX(updated_at)`»).

### 3.2. Сервер

```sql
ALTER TABLE users_female
  ADD COLUMN phone_number           TEXT UNIQUE,   -- E.164; у email-пользователей NULL
  ADD COLUMN data_revision          BIGINT NOT NULL DEFAULT 1,
  ADD COLUMN profile_revision       BIGINT DEFAULT 1,  -- когда менялся профиль
  ADD COLUMN firebase_import_status TEXT,
  ADD COLUMN firebase_import_error  TEXT;

CREATE TABLE cycles (
  user_id       TEXT NOT NULL,
  start_day     INTEGER NOT NULL,
  period_length INTEGER,                           -- NULL = tombstone
  ovulation     JSONB,
  revision      BIGINT NOT NULL,
  PRIMARY KEY (user_id, start_day)
);

CREATE TABLE flow_levels (
  user_id    TEXT NOT NULL,
  day_number INTEGER NOT NULL,
  level      INTEGER,                              -- NULL = tombstone
  revision   BIGINT NOT NULL,
  PRIMARY KEY (user_id, day_number)
);

CREATE TABLE comments (
  user_id    TEXT NOT NULL,
  day_number INTEGER NOT NULL,
  comment    TEXT,                                 -- NULL = tombstone
  revision   BIGINT NOT NULL,
  PRIMARY KEY (user_id, day_number)
);

CREATE TABLE user_tags (
  user_id  TEXT NOT NULL,
  id       TEXT NOT NULL,
  name     TEXT,                                   -- NULL = tombstone
  category INTEGER NOT NULL,
  revision BIGINT NOT NULL,
  PRIMARY KEY (user_id, id)
);

CREATE TABLE day_tags (
  user_id    TEXT NOT NULL,
  day_number INTEGER NOT NULL,
  tag_ids    JSONB NOT NULL DEFAULT '[]',          -- [] = «тегов нет», НЕ tombstone
  revision   BIGINT NOT NULL,
  PRIMARY KEY (user_id, day_number)
);

ALTER TABLE user_devices
  ADD COLUMN timezone     TEXT,         -- IANA (Europe/Moscow), не смещение
  ADD COLUMN last_seen_at TIMESTAMPTZ;  -- пишется на каждом /data/sync

CREATE INDEX ON cycles      (user_id, revision);
CREATE INDEX ON comments    (user_id, revision);
CREATE INDEX ON flow_levels (user_id, revision);
CREATE INDEX ON user_tags   (user_id, revision);
CREATE INDEX ON day_tags    (user_id, revision);
```

Индексы обязательны: без них pull — seq scan.

**`profile_revision`, а не `revision`.** На `users_female` рядом живёт `data_revision`, и два поля с именами `revision` и `data_revision` на одной таблице — это опечатка в pull-запросе, которая ждёт своего часа: перепутать их значит либо никогда не отдавать профиль, либо отдавать его на каждом прогоне.

**Оба счётчика начинаются с единицы, а не с нуля.** Строка пользователя рождается с содержимым — имя, почта, настройки, — а профиль отбирается на pull по `profile_revision > since`, и на первом прогоне `since = 0`. Пара «`data_revision = 0`, `profile_revision IS NULL`» означает, что профиль не приедет никогда, пока `users_female` не тронет что-нибудь постороннее, — то есть **D2**, оставленный открытым для каждого созданного дальше пользователя. Ноль сам по себе нигде не сравнивается: контракту нужно только, чтобы содержимое новой строки было строго больше стартового курсора.

Единица именно в `DEFAULT`, а не в создающем коде, потому что INSERT'ов в `users_female` больше одного (`createFemale`, `migrateUser`, дальше импорт), и забытый счётчик в новом — отказ без ошибки и без записи в лог. Строки, существовавшие до миграции, по той же причине бэкфилятся на ревизию 1, и `data_revision` вместе с ними: он не имеет права быть ниже максимальной ревизии под собой, иначе следующий push выдаст уже использованный номер.

### 3.3. Инварианты

1. **Ключи естественные и независимые от устройства** — `start_day`, `day_number`, UUID тега. Маппинга client-id ↔ server-id нет, upsert идемпотентен по построению. Новые сущности проектировать так же.
2. **FK на `tag_ids` не ставится.** В реальных данных сироты у двух пользователей из трёх: тег удалён, привязки к дням остались. Клиент их проглатывает — `compactMap` в `DayDisplayStateComputer.swift:31`.
3. **Удаление всегда tombstone.** Физическое удаление возможно в двух случаях, и оба — не доменные: wipe и отказ с `row: null` (§4.2), то есть сервер сообщил, что под этим ключом у него ничего нет. Второй случай не исключение из правила, а его конец: строке, которую сервер не признаёт, некому больше рассказывать о своём удалении. `deleteCycle(startDay:)` уходит из доменного кода.
4. **`revision` проставляется одним значением на транзакцию**, не на строку. Пишущий путь ровно один — `applyBatch`; импорт из Firebase идёт через него же.
5. **`day_tags` не имеет tombstone.** День, с которого сняли все теги, сохраняет строку с `tag_ids = []`. Пустой массив и есть удаление; сервер не должен его выбрасывать.
6. **Поцикловое — в строке цикла, подневное — в своей таблице по дню.** См. §3.4.
7. **Одна транзакция не пишет больше строк, чем помещается на страницу** (§4.4). Это инвариант, а не совет: на нём стоит правило курсора.
8. **Любая запись в профиль двигает `data_revision`** — откуда бы она ни пришла (§4.4, «Правило ревизии профиля»).

### 3.4. Почему выделения вынесены из цикла

`flow_levels` были единственными подневными данными, лежащими в поцикловой строке: комментарии и теги дня давно имеют свои таблицы с ключом по дню. Всё остальное в `CycleRecord` — `startDay`, `periodLength`, `ovulation` — свойства цикла.

Пока словарь лежал внутри строки, единицей синхронизации была вся строка, и два устройства, отметившие выделения в **разные дни одного цикла**, теряли одну из отметок. Отдельная таблица убирает конфликт по построению, а не правилом слияния.

**Схлопывается больше, чем этот случай.** Сейчас `handleSetFlowLevel` делает read-modify-write всей строки цикла: отметка на третий день делает грязным весь цикл, и он конфликтует также с правкой `period_length` и `ovulation` на другом устройстве. После выноса запись — один upsert одной строки, цикл не трогается.

**Валидация остаётся:** `canSetFlowLevel(at:today:)` по-прежнему спрашивает цикл, но только чтобы разрешить, а не чтобы писать.

**Окно уже есть.** `lastFlowDay(notAfter:)` уже ограничивает выборку `[startDay, startDay + maxPeriodLength − 1]` — потому что словарь и сегодня содержит ключи вне периода своего цикла (см. комментарий к методу). Над картой дней та же логика работает без изменений, меняется только источник.

**Наблюдение за `flow_levels` — по диапазону, как комментарии, и это безопасно.** `computeDayDisplayStates` зовёт `lastFlowDay` для каждого цикла, включая те, что начались до `loadedRange`. Данных о днях ниже нижней границы у него не будет — и это ничего не портит: `lastFlowDay` берёт **максимум**, а максимальный день с выделениями по построению совпадает с концом рисуемой полосы. Если полоса видна в диапазоне, то и её последний день с выделениями в диапазоне. Потерять можно только те дни, полоса которых целиком ниже окна, а её и не рисуют.

**Удаление цикла не удаляет выделения.** Это осознанное следствие: «обильные 5 марта» — наблюдение о дне, а не о том, как ведётся учёт. Исправила дату начала — наблюдения переживают исправление. Осиротевшая строка невидима: `DayDetailsView` показывает блок только при непустом `context.recorded`, а `lastFlowDay` ограничен окном своего цикла и чужой день не подхватит. Та же ситуация, что с сиротами `day_tags`, и разрешается так же.

**Что остаётся в строке цикла.** `periodLength` и `ovulation` — две поцикловые величины, и правка их с разных устройств по-прежнему разрешается last-write-wins. Это не потеря, а настоящий конфликт: оба утверждения про один цикл, и одно из них новее.

### 3.5. Как DDL попадает в базу

Решение дефекта **D10**. Порядок работ начинается не с таблиц, а с инструмента, которым их создают.

**Сначала — снять фактическую схему.** README утверждает, что таблицы создаются автоматически; кода для этого нет, значит содержимое базы неизвестно. До написания единой миграции выполнить на **обоих** окружениях:

```sql
SELECT table_name, column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN ('users_female','user_devices','cycles','comments',
                     'user_tags','day_tags','notification_schedule')
ORDER BY table_name, ordinal_position;
```

Результат решает, чем является §3.2 — `CREATE TABLE` или `ALTER TABLE` под уже существующую форму. Писать миграцию до этого запроса нельзя: `CREATE TABLE cycles` на существующей таблице упадёт, а `CREATE TABLE IF NOT EXISTS` тихо оставит чужую форму.

**Инструмент.** `app/migrations/NNN_name.sql` плюс `app/scripts/migrate.js` — по образцу `scripts/cleanup_expired_data.js`, который уже живёт в этой папке и запускается тем же способом. Раннер:

- заводит `schema_migrations (name TEXT PRIMARY KEY, applied_at TIMESTAMPTZ NOT NULL DEFAULT now())`;
- применяет неприменённые файлы по возрастанию имени, **каждый в своей транзакции**, и записывает имя в ту же транзакцию;
- при ошибке останавливается и выходит с ненулевым кодом.

**Запуск — вручную, staging первым.** DDL под `ALTER TABLE ... ADD COLUMN UNIQUE` берёт блокировку, и решать, когда её брать, должен человек — поэтому запуск никогда не висит на push, только на явном действии.

По SSH, как раньше:

```
cd /home/c107255/staging.calendar.red/app && node scripts/migrate.js
```

Либо через GitHub Actions — workflow "Run DB Migrations" (`.github/workflows/migrate.yml` в `redcalendar-api`), запускается вручную (`workflow_dispatch`) с выбором окружения (production/staging); вывод раннера виден прямо в логе запуска.

**Никаких DDL из кода приложения.** Пул на 10 соединений и `touch ../reload` — не то место, где создаются таблицы. Утверждение README про автосоздание удаляется как неверное.

## 4. Контракт `POST /data/sync`

### 4.1. Запрос

```
POST /data/sync
Authorization: Bearer <device_id>
Content-Type: application/json

{
  "since": 0,
  "sync_schema": 1,
  "device": { "timezone": "Europe/Moscow" },
  "changes": {
    "cycles":      [{ "start_day": 8467, "period_length": 0, "ovulation": null }],
    "flow_levels": [{ "day_number": 8468, "level": 2 }],
    "comments":    [{ "day_number": 9316, "comment": "..." }],
    "user_tags":   [{ "id": "...", "name": "S", "category": 3 }],
    "day_tags":    [{ "day_number": 9318, "tag_ids": ["..."] }],
    "profile":     { "name": "...", "settings": { ... } }
  }
}
```

`changes.profile` принимает **только** `name` и `settings`. См. §4.4.

`changes` может отсутствовать целиком — это pull-only прогон, и он же первый прогон установки (§5.2).

`sync_schema` — поколение набора таблиц, которое понимает эта сборка клиента. Сегодня `1`. См. §4.6.

`device` — текущее состояние устройства, отправляется на каждом прогоне. Сервер обновляет `user_devices.timezone` и `last_seen_at`. Это заготовка под уведомления: пояс — чтобы попасть в 9 утра по местному, `last_seen_at` — чтобы не будить того, кто заходил пять минут назад. Сами уведомления проектируются отдельно (§15).

### 4.2. Ответ

```json
{
  "user_id": "hb9X1EMKxZXqqETMkBO3M0OvZh53",
  "changes": { "cycles": [], "flow_levels": [], "comments": [], "user_tags": [], "day_tags": [], "profile": null },
  "rejected": [{ "table": "cycles", "key": 8467, "reason": "...", "row": null }],
  "next_cursor": 57,
  "has_more": false,
  "full_resync_required": false,
  "import_status": "done"
}
```

Строки в `changes` несут своё поле `revision`. В `rejected` поле `row` — авторитетная серверная строка, либо `null`, что означает «удалить локально».

`key` — естественный ключ строки, как её прислал клиент: по нему он и находит у себя ту, что отправлял. Ключ, выходящий за границы §4.5, возвращается как есть, но `row` при нём всегда `null` — искать нечего, и сам запрос за таким ключом уронил бы транзакцию (`22003` на `INTEGER`). Ключ, который вовсе не скаляр, вернуть нечем: `key` приходит `null`. Отвергнутый профиль лежит там же, с `"table": "profile"` и `"key": null`.

Ответ 200 — ровно этот объект, без обёртки `success`/`timestamp`, которая есть у auth-эндпоинтов: у прогона нет частичного успеха, а `rejected` — не ошибка. Ответы 4xx и 5xx, наоборот, идут в общей обёртке (`success`, `error`, `message`) — их разбирает та же клиентская ветка, что и ошибки входа (§5.7).

`full_resync_required` сервер сегодня не выставляет никогда — но поле есть в ответе с первого дня, и клиент его чтит с первого дня. См. §4.6.

### 4.3. Алгоритм сервера — одна транзакция

```
BEGIN;                                    -- READ COMMITTED, по умолчанию

1. device_id → user  (authService.verifyDevice; 401, если устройства нет)

2. Захват строки пользователя. Ровно один из двух вариантов, и он выполняется ВСЕГДА:

   changes непусты:
     UPDATE users_female SET data_revision = data_revision + 1
      WHERE id = $1 RETURNING data_revision              -- → R, эксклюзивная блокировка

   changes пусты:
     SELECT data_revision FROM users_female
      WHERE id = $1 FOR SHARE                            -- R = NULL, разделяемая блокировка

3. Валидация построчно (§4.5). Принятые → upsert с revision = R.
   Отвергнутые → в rejected вместе с авторитетной строкой.

4. Pull по каждой таблице + профиль — по правилу страницы (§4.4).

5. UPDATE user_devices
       SET timezone = COALESCE($2, timezone), last_seen_at = now()
     WHERE device_id = $1

6. COMMIT.

7. После коммита, и только если транзакция что-то записала (`R` выделен), —
   silent push всем устройствам пользователя, кроме вызвавшего.
```

**«`changes` непусты» — это хотя бы одна строка хотя бы в одной таблице либо непустой `profile`.** Не наличие ключа: `{"cycles": []}` — пустой запрос. Иначе каждый прогон выделяет ревизию, `data_revision` растёт без причины, а `next_cursor` уезжает на номер, за которым ничего не стоит.

**Считается по принятым строкам, а не по присланным, и потому шаг 3 выполняется раньше шага 2.** Валидация чистая — ничего не читает и не пишет, — так что порядок в списке выражает зависимость по данным (upsert не встанет раньше, чем выделен `R`), а не время. Батч, у которого отвергнута каждая строка, не пишет ничего, и ревизию под него выделять нельзя по тому же правилу, что и под пустой: номер, за которым не стоит ни одной строки.

**Шаг 7 — условный.** Пуш уходит, только если что-то записано. APNs отмеряет фоновые пуши порядка 2–3 в час на устройство (§7); израсходовать их на прогоны, ничего не изменившие, — значит не доставить тот, который что-то менял.

«Что-то записано» — это выделенный `R`, а не число строк: батч из одного только `profile` не пишет ни строки таблиц, но второму устройству о смене имени или настроек знать надо ровно так же.

**Шаг 2 обязателен и на pull-only прогоне.** «Одна транзакция» в Postgres при уровне READ COMMITTED не даёт единого снимка: каждый оператор берёт свой. Шаг 4 — это шесть отдельных `SELECT`, и без блокировки между первым и последним успевает закоммититься чужая транзакция. Тогда `cycles` прочитаны до ревизии 50, `comments` — до 57, курсор уедет на 57, и строки `cycles` из 51…57 не попадут ни в эту страницу, ни в следующую. На пишущем пути этого не было и раньше: `UPDATE ... RETURNING` держит эксклюзивную блокировку до конца, и никакой другой писатель этого пользователя закоммититься не успевает. `FOR SHARE` даёт то же самое читателю, при этом два одновременных pull-only друг друга не блокируют.

Альтернатива — `BEGIN ISOLATION LEVEL REPEATABLE READ`. Она не выбрана: понадобился бы цикл повторов на `40001 serialization_failure`, а блокировка строки пользователя на пишущем пути и так уже есть, и она делает оба пути одинаковыми.

Условие `revision < R` на шаге 4 исключает собственные только что записанные строки: клиент и так знает их содержимое. На ревизии `R` лежат строки ровно этой транзакции — строка пользователя заблокирована, чужая запись не могла в неё попасть.

Шаг 5 не трогает `data_revision`: состояние устройства не пользовательские данные, синхронизировать его между устройствами незачем. `COALESCE` — чтобы отсутствующая секция `device` не занулила уже известный пояс. Пояс, не похожий на IANA-идентификатор, отбрасывается наравне с отсутствующим: колонка заведена под уведомления, а неверный пояс там хуже пустого — по пустому видно, что слать пока некуда.

### 4.4. Правила

**Правило страницы.** Каждая таблица читается так:

```sql
SELECT ... FROM <table>
 WHERE user_id = $1
   AND revision > $since
   AND ($R::bigint IS NULL OR revision < $R)
 ORDER BY revision
 LIMIT $limit + 1
```

`limit + 1` — чтобы отличить «строки кончились» от «страница кончилась».

Для каждой таблицы `T`:

- вернулось `≤ limit` → не усечена, `maxRev(T)` = максимум возвращённых;
- вернулось `limit + 1` → усечена; лишняя строка выбрасывается, `maxRev(T)` = ревизия последней оставшейся. Если она совпала с ревизией выброшенной, страница режет ревизию пополам — спускаемся к предыдущей **отличной** ревизии. Если отличной не осталось, инвариант §3.3.7 нарушен: одна ревизия не помещается на страницу. Тогда она отдаётся целиком, невзирая на `limit`, — иначе клиент зациклится, вечно перечитывая её начало.

Дальше:

- ни одна таблица не усечена → `next_cursor = max(все возвращённые revision, и R, если он выделялся)`, `has_more = false`;
- усечена хотя бы одна → `boundary = min(maxRev(T))` по **усечённым** таблицам; из **всех** таблиц выбрасываются строки с `revision > boundary`; `next_cursor = boundary`, `has_more = true`.

> Максимум по всем фактически возвращённым строкам — ошибка, и правило размера транзакции её не ловит: оно про разрез *внутри* ревизии, а этот разрез — *между таблицами*. Пусть у `cycles` 1500 строк на ревизиях 1…1500, а у `comments` три на 1600…1602. `cycles` усечётся на 1000, `comments` вернётся целиком, максимум = 1602. Клиент поднимет курсор до 1602, и строки `cycles` 1001…1500 больше никогда не попадут под `revision > since`. Минимум по усечённым с обрезкой остальных — единственное значение, при котором «всё, что ≤ курсора, доставлено» остаётся правдой.

**Профиль — такой же поток, как таблица.** Усечься он не может, строка одна, но обрезке по `boundary` подчиняется наравне со всеми. Освободи его от неё — и усечённая страница увезёт курсор за его `profile_revision`, выбросив по дороге сам профиль; `profile_revision > since` больше никогда не выполнится, и второе устройство не узнает ни имени, ни номера.

**Правило курсора.** `next_cursor` вычисляется **только** так, как описано выше. Никогда не текущий `data_revision` пользователя.

> Иначе параллельная транзакция коммитится между чтением строк и чтением счётчика, курсор уезжает на ревизию, строки которой мы не отдали, и они теряются навсегда.

**Правило размера транзакции.** Транзакция не пишет больше строк, чем помещается на страницу.

> Иначе одна ревизия разрежется между страницами. Ветка «отдать ревизию целиком» выше — аварийный выход, а не режим работы: она нарушает `limit` и может отдать страницу произвольного размера.

Практически: `limit = 1000`, клиент бьёт push на пачки, импорт пишет чанками по 200–500. При наблюдаемом максимуме ~260 строк на пользователя вторая страница не встретится, но код на неё рассчитан.

**Батч сверх страницы сервер всё-таки применяет.** Отвергнуть его значило бы заблокировать навсегда клиента, который так делает, — а починить его можно только выпуском. Аварийная ветка правила страницы этот случай выдерживает, поэтому батч пишется, а нарушение инварианта уходит в лог. Разрешением это не становится: платит за него не тот, кто прислал, а чужое устройство, которому приедет страница произвольного размера.

**Правило личности.** Профиль делится надвое:

| Поле | Кто пишет |
|---|---|
| `name`, `settings` | устройство и сервер |
| `phone_number`, `email` | **только сервер**, в `changes` игнорируются |

> Номер и email — это логин, по ним работают `check-phone` и `check-email`. Прими сервер их из `changes.profile` — и кривой или враждебный клиент перепишет, кому принадлежит аккаунт, после чего заберёт его обычным входом.

**Правило ревизии профиля.** Любая запись в `users_female` — из `/data/sync`, из ступени 2 `check-phone`, из импорта, из `updateFemaleEmail` — идёт через один хелпер, который в **той же** транзакции делает `data_revision = data_revision + 1` и кладёт новое значение в `profile_revision`.

> Без этого устройство никогда не узнает собственный номер и почту: pull профиля отбирается по `profile_revision > since`, а `check-phone` и импорт пишут вне транзакции синхронизации. Тихо, необратимо и заметно только на втором устройстве.
>
> `femaleService.getFemaleById` при этом надо расширить: сейчас он не выбирает `phone_number` (`female.js:44`).

**Tombstone'ы не чистятся.** Объём — строка в день на пользователя. Если когда-нибудь начнём чистить, понадобится `full_resync_required` для устройств с курсором ниже горизонта; поле для этого уже есть (§4.6).

### 4.5. Валидация

Построчная, а не «весь батч или ничего» — иначе одна плохая строка блокирует устройство навсегда.

Границы для правок из приложения — узкие (`canStartPeriod`, `Constants.Cycle.maxPeriodLength = 14`). Для импорта — широкие, только защита от мусора:

| Поле | Tombstone | Наблюдается в реальных данных | Граница импорта |
|---|---|---|---|
| `day_number` | — | 6550 … 9368 | −20000 … 40000 |
| `cycles.period_length` | `null` | `null`, 3 … 16 | `null` или 0 … 60 |
| `cycles.ovulation` | — | — | не проверять |
| `flow_levels.level` | `null` | строго `{1, 2, 3}` | `null` или 1 … 3 |
| `comments.comment` | `null` | до 267 байт UTF-8 | `null` или ≤ 2000 символов |
| `user_tags.id` | — | UUID | непустая строка, ≤ 200 символов |
| `user_tags.name` | `null` | — | `null` или ≤ 200 символов |
| `user_tags.category` | — | 2, 3 | любой `Int` |
| `day_tags.tag_ids` | нет, пустой `[]` | — | массив строк, ≤ 100 элементов |
| `profile.name` | — | — | `null` (стереть) или строка ≤ 200 символов |
| `profile.settings` | — | — | `null` или объект |
| длина цикла | — | 19 … 85 | не проверять |

**`null` в колонке tombstone — это не «поле пропущено», это «удали».** Отвергнуть его значит сделать удаление невозможным: `DayDetailsView.swift:209` предлагает `(nil, "Не указано")` для выделений, пустой комментарий сохраняется как `nil`, удаление тега — это `name = nil`. Три из пяти таблиц удаляются именно так, и валидатор обязан их пропускать.

`category` принимается любым целым намеренно: `UserTagRecord.category` — это `Int`, а не `TagCategory`, ровно чтобы будущая версия клиента не была отвергнута сервером.

**Зеркальное правило: где tombstone'а нет, там пропуск поля — отказ.** `user_tags.category` и `day_tags.tag_ids` объявлены `NOT NULL`, и строка без них — это не «поле не менялось», а `23502` посреди транзакции, уносящий с собой весь батч, включая чужие исправные строки. Строка отвергается ровно затем, чтобы этого не случилось; ей в ответ уезжает серверная версия.

**`ovulation` не проверяется вовсе.** Границы для неё в таблице нет, а любое значение JSON в `JSONB` ложится. Придумать ей форму здесь — значит отвергнуть строки, которые следующая версия клиента имеет право написать, и узнать об этом через месяц.

**Профиль проверяется на форму, а не на содержимое.** `settings` уходит в `JSONB`, и скаляр там клиент не разберёт обратно — а разобрать он обязан, иначе настройки не приедут ни на одно устройство. Поля, которые устройство писать не может, при этом не отвергаются, а игнорируются: это разные вещи, и правило личности выше — про вторую.

Если применить к импорту границы приложения, будут отвергнуты реальные данные: период в 16 дней и цикл в 19 дней.

**Обратная сторона: на клиент приедет то, что клиент сам создать не может.** Период в 16 дней при `maxPeriodLength = 14`, циклы в 19 дней при `minCycleLength = 20`. Доменные запросы это переживают — `periodCoverage` считает от `periodLength` как есть, `owningCycle` про минимальную дистанцию не знает, — а пользователь просто не сможет создать такой цикл заново, если удалит. **На pull-пути клиент не валидирует ничего**: сервер авторитет, а локальная проверка означала бы строку, которую невозможно ни принять, ни удалить. И `Constants.Cycle` расширять под эти данные нельзя: они описывают, что можно ввести, а не что может приехать.

### 4.6. Эволюция набора таблиц

Курсор глобальный: одно число на все таблицы. Значит добавление шестой таблицы данных в будущем — не «клиент её пока не понимает», а тихая потеря.

Старый клиент разберёт ответ своей `Codable`-структурой, неизвестный ключ в `changes` проигнорирует — **и всё равно поднимет курсор**. Строки новой таблицы окажутся ниже его курсора навсегда; когда он обновится, он их уже не запросит.

Два механизма, оба стоят по несколько строк и оба должны существовать до первой раскатки:

1. **`known_tables` в `sync_state`.** Клиент хранит набор таблиц, которые понимает эта сборка. При запуске: если набор в коде **шире** сохранённого — `cursor = 0`, набор перезаписывается. Полный ресинк идемпотентен (upsert по естественному ключу), так что это безопасно и стоит одного лишнего прогона на обновление.
2. **`full_resync_required` в ответе.** Сервер выставляет `true`, когда сам решил, что курсор устройства ниже горизонта — сегодня такого случая нет, он появится при чистке tombstone'ов. Клиент, получив `true`, ставит `cursor = 0` и начинает круг заново, **не применяя** остальную часть этого ответа.

Поле надо завести сразу, а не когда понадобится: клиент, который его не читает, не начнёт читать задним числом, и именно он и окажется тем, у кого потерялись данные.

`sync_schema` в запросе — диагностика: он ничего не решает на сервере сегодня, но позволяет увидеть в логах, какие поколения клиентов ещё ходят, и служит крючком, если сервер когда-нибудь должен будет фильтровать таблицы по версии.

## 5. Прогон синхронизации на клиенте

Один прогон за раз — флаг в `SyncMiddleware`.

### 5.1. Алгоритм

1. Прочитать `sync_state`. `known_tables` уже, чем в коде → `cursor = 0`, набор перезаписать (§4.6).
2. **Если `sync_state.user_id` пуст — прогон идёт без `changes`** (§5.2), и это делает его **pull-only**. Иначе шаг 3.
3. Прочитать грязные строки всех шести таблиц **одной read-транзакцией**; `sent_max` — максимум `dirty_seq` **по фактически прочитанным строкам**, а не отдельным запросом (§5.4).
4. `POST /data/sync`.
5. **Проверка владельца:** `response.user_id != sync_state.user_id` и он не `nil` → `wipe`, прогон заново. Если `sync_state.user_id` пуст — записать.
6. **`full_resync_required` → `cursor = 0`, остальное из ответа не применять, следующий круг.**
7. **Одна транзакция, строго в этом порядке:**
   1. применить `changes`, **пропуская строки с `dirty_seq IS NOT NULL`**;
   2. **если прогон не pull-only** — `UPDATE ... SET dirty_seq = NULL WHERE dirty_seq <= sent_max`;
   3. применить `rejected` — записать `row` либо удалить локальную строку, **всегда снимая `dirty_seq`**;
   4. `cursor = next_cursor`, плюс `import_status` из ответа (§10.4) и `user_id`, если строка его ещё не несёт.
8. `has_more` → сразу следующий круг, без дебаунса.

Курсор двигается только внутри транзакции шага 7. Приложение убили посередине — транзакция откатилась, курсор на месте, следующий прогон перечитает. Идемпотентно.

**Проверка владельца стоит раньше `full_resync_required`**, хотя выглядит менее срочной: `wipe` включает в себя полный ресинк и делает его бессмысленным, а обратный порядок стоил бы лишнего круга.

**Шаг 7.2 не выполняется вовсе, когда `sent_max` не определён** — на pull-only прогоне, и точно так же на обычном, у которого не нашлось ни одной грязной строки. Читать было нечего. Подставить вместо него ноль безобидно, но написать «снять все флаги» — значит объявить всю локальную базу отправленной. Сразу после миграции v3 это вся история пользователя: бэкфилл ставит `dirty_seq = 1` каждой строке, а первый прогон установки как раз pull-only.

**Пропуск грязных строк на шаге 7.1 не теряет серверные данные, хотя после того же бэкфилла грязно всё.** Пропускаются только ключи, у которых уже есть локальная версия, — и она уедет следующим кругом и победит, потому что push идёт раньше pull, а это и есть правило. Ключа, которого локально нет, грязным быть не может: пропускать нечего, он применяется всегда. А если локальную версию сервер не примет, его собственная строка вернётся в `rejected` (шаг 7.3), не в `changes`.

**Отказ по профилю — единственный, где `row: null` не удаляет.** Строка `user_profile` одна и несёт `user_id` владельца, а владелец серверный: удалить её, потому что сервер не принял имя, значит выбросить заодно и личность, которую мы не отправляли. Флаг снимается, строка остаётся.

**Круг ограничен сверху.** `has_more`, повтор после `wipe` и повтор после `full_resync_required` — три ветки одной петли, и крутит её ответ сервера. При странице в 1000 строк против наблюдаемого максимума ~260 на пользователя второй страницы не бывает вовсе, так что потолок ничего не стоит и ловит единственный настоящий случай: сервер, который всегда отвечает `has_more`. Достигнутый потолок — запись в лог и выход до следующего триггера, не отказ.

**Шаг 7.3 — единственное место, где правка «в полёте» теряется.** Если пользователь правил ту же строку, пока запрос летел, её `dirty_seq > sent_max` и шаг 7.2 её пощадил — но шаг 7.3 всё равно записывает серверную версию поверх и снимает флаг. Это прямое следствие решения 5: сервер уже сказал, что нашу строку не принимает, и второй экземпляр той же отвергнутой правки он не примет тоже. Достижимо это редко — клиентские границы уже серверных (§4.5), — но правило должно быть записано, иначе его реализуют наугад.

### 5.2. Почему первый прогон установки — pull-only

Проверка владельца (шаг 5) стоит **после** запроса. Пока `sync_state.user_id` не установлен, отправлять что-либо нельзя: если база принадлежит предыдущему пользователю, шаг 4 зальёт её данные в чужой аккаунт, и wipe на шаге 5 отменит только локальную копию.

Путь достижим и он ровно тот, который §6 пытается закрыть: 401 при синхронизации → `.notAuthenticated`, база сохраняется по решению 6 → `AuthMiddleware.swift:203` стирает device ID → экран входа → входит другой человек.

Поэтому: **пока `sync_state.user_id` пуст, `changes` не отправляются.** Ответ приносит `user_id`, он записывается, push начинается со следующего круга. Один лишний запрос ровно один раз за установку.

Основная же защита стоит раньше — при входе (§6): все три точки авторизации возвращают идентификатор пользователя, и сверить его можно до того, как синхронизация вообще началась.

### 5.3. Почему порядок применения именно такой

Сначала снять грязные флаги, потом применить pull — значит отдать наши только что отправленные строки на перезапись более **старой** версией с другого устройства. Пока флаг стоит, строка защищена. Отвергнутые применяются последними: сервер нас переспорил, его слово окончательное.

### 5.4. Почему `dirty_seq`, а не булев флаг

Между `await`-ами прогон отпускает главный актор, и `DatabaseMiddleware` на нём же пишет. Гонка:

```
1. строка X грязная, прогон её отправил
2. пока запрос в полёте, пользователь правит X ещё раз
3. ответ: X принята
4. булев флаг снят → вторая правка потеряна и никогда не уезжала
```

`local_seq` — монотонный счётчик в `sync_state`, инкремент в каждой локальной пишущей транзакции; его значение штампуется на изменённые строки.

**Инкремент, чтение счётчика и запись строк — одна транзакция, и делает это `DatabaseService`** (один `upsertStamped` на все пять таблиц), а не вызывающий. Middleware строит запись, но поколение ему взять неоткуда, и прочитанное вне транзакции даёт ровно ту же потерю, что и отдельный запрос за `sent_max` ниже, только на пишущей стороне. Правка, случившаяся в полёте, получает больший `dirty_seq` и не попадает под `dirty_seq <= sent_max`.

Проверка на членство в отправленном множестве не нужна: счётчик только растёт.

**Чтение и вычисление `sent_max` — одна транзакция.** Если прочитать строки, а максимум взять отдельным запросом, между ними успевает пройти локальная запись: строка уехала со значением 5, `sent_max` посчитан как 9, шаг 7.2 снимает флаг с правки, которая никуда не отправлялась. Это ровно та потеря, ради которой вся эта колонка и заведена, — только на один шаг раньше.

### 5.5. Транзакционность — это и производительность

Наблюдения GRDB срабатывают на каждую транзакцию и выкладывают в стор весь массив циклов, а редьюсер на каждом `.setCycles` гоняет `computeDayDisplayStates` по всему `loadedRange`. Построчное применение первого импорта — сотни обновлений состояния.

**Полный ресинк — это прогон, начинающийся с `cursor == 0`**: первый после установки, после `wipe`, после роста `known_tables` и после `full_resync_required`. На его время наблюдения ставятся на паузу и поднимаются один раз в конце. Определение нужно записать, потому что «полный» здесь не про число строк: ресинк на трёх строках тоже начинается с нуля и тоже проходит через паузу — цена в четыре перезапуска наблюдений платится раз на установку, а условие остаётся одним числом, а не эвристикой.

**Механика.** `cancelAll()` и `startPermanentObservations()` — приватные методы `DatabaseMiddleware`, и такими остаются: токены принадлежат ему. `SyncMiddleware` диспатчит `.sync(.beganFullResync)` и `.sync(.finishedFullResync)`, а `DatabaseMiddleware` **наблюдает** домен sync — матчит эти два случая и берёт `default` на остальные, ровно как `MigrationMiddleware` наблюдает одну ветку auth. Свои токены он при этом никому не отдаёт.

Два обязательства, оба легко потерять:

- пауза держится через **все** страницы `has_more`, а не по одной на круг;
- `.finishedFullResync` уходит на **любом** выходе, включая отказ и отмену (`defer`). Наблюдения, не поднявшиеся после неудачного ресинка, — это календарь, который перестал обновляться до перезапуска приложения.

### 5.6. Триггеры

| Событие | Задержка |
|---|---|
| `.auth(.set(.authenticated))` | сразу — это и есть старт после холодного запуска и после входа |
| Локальная запись | дебаунс 3 с, все грязные строки одним запросом |
| `scenePhase → .active` | сразу, через существующий `retryFailedTasks` |
| `scenePhase → .background` | сразу, флашим дебаунс |
| Silent push с `r > cursor` | сразу |
| `has_more` | сразу |

**Первая строка не декоративная.** `.onAppear` уходит целиком (§8), а `.onChange(of: scenePhase)` не срабатывает на начальном значении — без явного триггера холодный запуск не синхронизировался бы вообще. `.auth(.set(.authenticated))` — тот же сигнал, по которому `DatabaseMiddleware` заводит наблюдения (`DatabaseMiddleware.swift:62`), и он приходит и после восстановления сессии из keychain, и после свежего входа.

**Триггер локальной записи производит `DatabaseMiddleware`, а не `SyncMiddleware`.** Он диспатчит `.sync(.requested(.localEdit))` из своей единственной точки записи — приватного `write()`, через который проходит каждая транзакция, — и только после того, как та прошла. Очевидная альтернатива, матчить пишущие случаи `DataAction` в самом `SyncMiddleware`, неверна дважды: она пушит и по записям, которые упали, и молча пропускает следующий добавленный экшен редактирования — то есть ровно тот отказ, ради которого экшены и сгруппированы по доменам (`CLAUDE.md`, Redux). Знает, что данные легли на диск, только тот, кто их туда положил.

**Запись во время прогона не глотается.** Сработавший дебаунс при взведённом флаге «прогон идёт» не отменяется, а запоминается: по завершении текущего прогона немедленно запускается следующий. Иначе строка, отредактированная в неудачную секунду, ждёт следующего несвязанного триггера — то есть до сворачивания приложения.

Редактор комментария автосохраняется каждые 600 мс (`Constants.Sheets.autosaveDebounceNanoseconds`) — без дебаунса набор текста превратится в очередь HTTP-запросов.

### 5.7. Ошибки

| Ситуация | Действие | Индикатор |
|---|---|---|
| Нет сети (`URLError`), 5xx | backoff 2 → 60 с, сброс при успехе | `.pending` |
| 429 | backoff по `Retry-After` | `.pending` |
| 401 | `.notAuthenticated`, **базу не трогаем** | экран входа |
| 4xx на весь запрос | backoff, пометка проблемы | `.failed` |
| Строка отвергнута | сервер побеждает молча | — |
| Прогон отменён (`CancellationError`, `URLError.cancelled`) | ничего: ни backoff, ни ретрая | не трогаем |

Офлайн — не ошибка. Приложение спроектировано на работу без сети, красным это показывать нельзя.

`NWPathMonitor` не нужен: backoff с потолком в минуту закрывает «вернулась сеть при открытом приложении».

429 приходит теперь и от лимита на адрес (§16), а не только от лимита на адресат. Ветка та же — строка таблицы выше покрывает оба случая, и это ровно тот выигрыш, ради которого `Retry-After` читается, а не угадывается.

**Эта таблица требует починки D9.** Сегодня `validateHTTPResponse` (`APIService.swift:470`) отдаёт всё `>= 400` с разбираемым телом как `.serverError(String)`, а сервер всегда отдаёт разбираемое тело — 429, 500 и 400 неразличимы, `Retry-After` не читается. `validateHTTPResponse` остаётся единственной точкой обработки, но получает две новые ветки **до** общей:

```swift
case rateLimited(retryAfter: TimeInterval?, message: String?)   // 429
case serverUnavailable(status: Int, message: String?)           // 5xx
```

`.serverError(String)` и `.httpError(Int)` не меняются — иначе ломается `AuthenticationError.from` (`AuthenticationError.swift:79`), которая сопоставляет `.serverError(let message)`. Туда добавляются два случая, отображающие новые ошибки в `.serverError(message ?? ...)`: экраны входа сегодня показывают серверный текст `RATE_LIMITED` из `check-phone`, и это поведение должно сохраниться.

## 6. Владение базой

Три разных события, которые сейчас все схлопываются в `.notAuthenticated`:

| Событие | База | Почему |
|---|---|---|
| Явный logout | **стираем** | приватность — не оставлять цикловые данные на общем телефоне |
| 401 при синхронизации | не трогаем | устройство разлогинили с другого телефона, человек тот же |
| Вход другого пользователя | **стираем** | иначе данные предыдущего уедут в новый аккаунт |

**`wipe` — это данные плюс `sync_state`.** Пять таблиц данных, `user_profile`, и `sync_state` обратно в начальное состояние: `cursor = 0`, `local_seq = 0`, `import_status = NULL`, `user_id` — новый владелец либо `NULL`. Курсор здесь важнее самих данных: оставить его высоким значит получить пустую базу, которая никогда ничего не вытянет, потому что всё уже «ниже курсора». `known_tables` при этом сохраняется — он про сборку, а не про пользователя.

**Явный logout:** `DatabaseMiddleware` ловит `.auth(.logout)` — сначала `cancelAll()` наблюдений, потом `wipe`. В обратном порядке наблюдения сработают на очистку и на кадр покажут пустой календарь перед экраном входа.

Требует починки **D4**: `.logout` должен доходить до `.notAuthenticated` при любом исходе сетевого запроса. Пользователь попросил выйти — выход должен состояться. Без этого wipe может сработать при живой сессии.

**Смена пользователя проверяется при входе, а не при первой синхронизации.** Все три точки авторизации возвращают идентификатор: `verify-code` и `verify-flash-call` — `data.user.id`, `migrate` — `data.user_id`. Значит `AuthMiddleware` знает владельца до того, как что-либо будет отправлено:

```
успешный вход/миграция → сравнить полученный user_id с sync_state.user_id
  не совпал и sync_state.user_id не пуст → wipe, cursor = 0
  затем записать user_id в sync_state
```

Порядок важен: wipe до сохранения нового `device_id`, чтобы прерывание посередине оставило непротиворечивое состояние (старая база при старом устройстве, либо чистая база при новом).

**Все три строки этой схемы — одна транзакция**, `claimOwner(_:)`. Не чтение владельца с последующим вызовом `wipeAll`: решение о стирании обязано опираться на только что прочитанное значение, а между чтением и стиранием успевает начаться прогон §5 — тот самый, который шагом 7.4 как раз и дописывает `user_id`. То же соображение, по которому шаг 1 прогона — транзакция, а не два запроса. `wipeAll` и `claimOwner` делят внутреннюю `wipe(_:newOwner:)`, чтобы «что именно стирается» было записано один раз.

**Стереть базу мало — надо стереть и то, что из неё уже прочитано.** `AppState.userProfile` заполняется наблюдением, а наблюдения к моменту wipe уже отменены: строки нет, а имя и настройки цикла предыдущего аккаунта остаются в памяти до перезапуска. Поэтому `.notAuthenticated` обнуляет `userProfile` там же, где обнуляет `calendarState` и `syncState`. Правило общее: значение, доставаемое из стираемых таблиц, снимается в редьюсере вместе со сбросом остального, а не полагается на то, что наблюдение пришлёт `nil`.

**Прогон, начавшийся до выхода, обязан прекратиться.** Отменять снаружи нечего: прогон — это `Task`, который никто не держит, а ждёт он сети, и вредит не ожидание, а применение ответа. Поэтому `SyncMiddleware` держит `sessionEpoch`, увеличивает его на `.auth(.logout)` и на `.auth(.set(.notAuthenticated))`, снимает значение на старте прогона и сверяет в двух местах: в начале каждого круга и непосредственно перед `applySync`. Второе и есть существенное — всё, что выше, только читает, а wipe успевает лечь ровно пока запрос в полёте. Без этой сверки ответ, выписанный ушедшему пользователю, применяется в уже очищенную базу и двигает курсор: выход оставляет на телефоне и чужие строки, и курсор, при котором их больше нечем вытеснить.

Проверка в §5.1 (шаг 5) остаётся второй линией и покрывает случай, когда `sync_state.user_id` пуст — обновление с v3.2, где его неоткуда взять. Там она работает вместе с правилом pull-only (§5.2): пока владелец неизвестен, отправлять нечего.

Оставшийся щербатый случай — установка v3.2, на которой сменился пользователь **до** обновления. Проверить это нечем: `sync_state` тогда ещё не существовало, а в keychain лежит только `device_id`. v3.3 не раскатана, таких установок в природе нет; фиксируется как известное ограничение бэкфилла, а не как задача.

## 7. Silent push

```
apns-push-type:   background
apns-priority:    5
apns-collapse-id: sync

{ "aps": { "content-available": 1 }, "r": 57 }
```

Ревизия в payload даёт устройству отсеять себя без обращения к сети — это и есть то, за что iOS не душит фоновые пуши.

`apns-collapse-id: sync` безопасен именно потому, что pull кумулятивен: схлопывание нескольких пушей в последний не теряет ревизий, а только сокращает число пробуждений.

**Silent push — оптимизация, а не механизм.** APNs background push rate-limited Apple (порядка 2–3 в час на устройство), не доставляется при принудительно закрытом приложении, задерживается в Low Power Mode. Синхронизация обязана запускаться сама по триггерам §5.6.

Кому слать: всем устройствам пользователя, кроме вызвавшего (`device_id != caller`).

### 7.1. Что для этого надо поменять в `push.js` (**D8**)

Две правки, обе за пределами «отдельного билдера payload»:

- **`getUserTokensByEnvironment(userId)` (`push.js:78`) выбирает только `apns_token`.** Исключить вызвавшего нечем. Сигнатура становится `getUserTokensByEnvironment(userId, { excludeDeviceId })`, выборка добавляет `AND ($2::text IS NULL OR device_id <> $2)`.
- **Тип и приоритет захардкожены в `sendToEndpoint` (`push.js:198-199`), а не в `sendToUser`.** Один билдер payload проблему не решает: параметризовать надо и заголовки. `sendToEndpoint(token, payload, endpoint, { pushType, priority })`, а `sendToUser` расщепляется на `sendAlertToUser` (существующее поведение, `alert`/10) и `sendSyncToUser` (`background`/5).

Существующий alert-путь остаётся нетронутым для будущих напоминаний.

Отдельно — **D7**: `POST /push/send` принимает `user_id` в теле и не проверяет ничего. У эндпоинта нет вызывающего — ни в коде, ни в планах, ближайший кандидат (§15, планировщик уведомлений) ещё не спроектирован — так что закрывается он удалением `api/push.js`, а не авторизацией на нём. `sendAlertToUser` остаётся в `services/push.js` как точка входа для того планировщика, когда он появится.

## 8. Жизненный цикл приложения

Решение дефекта **D3**.

```swift
// AppStore — lazy static let, как ServiceLocator, Configurator, DatabaseMiddleware
extension AppStore { static let shared = AppStore(...) }

// AppDelegate.didFinishLaunchingWithOptions
Configurator.shared.setup()
AppStore.shared.send(.auth(.check))
AppStore.shared.send(.analytics(.checkStatus))
AppStore.shared.send(.appearance(.checkAccentTheme))

// AppDelegate.didReceiveRemoteNotification(_:fetchCompletionHandler:)
// сравнить r из payload с курсором → syncNow → completion

// RedCalendarApp
@StateObject private var store = AppStore.shared
// .onAppear уходит целиком; .onChange(of: scenePhase) остаётся
```

**Почему `didFinishLaunchingWithOptions`:** документированная точка «ровно один раз за процесс», выполняется при фоновом запуске, и там же доступен `launchOptions[.remoteNotification]`.

**Порядок внутри неё обязателен.** `Configurator.shared.setup()` — первым: `AppStore.shared` это `lazy static let`, его вычисление зовёт `combineAppMiddlewares()`, и любое разрешение сервиса до регистрации — `fatalError` в `ServiceLocator`. Правило из `CLAUDE.md` («ничто не разрешает сервис во время конструирования») от переноса не отменяется, только меняет место.

**Почему `@StateObject` над готовым синглтоном:** сохраняет наблюдение ровно таким, какое оно сейчас — включая `.tint(store.state.accentTheme.accent)` в теле `App`, которое перестало бы обновляться, стань стор обычным ненаблюдаемым свойством.

**Отвергнутая альтернатива:** стор в `AppDelegate`, приложение читает `appDelegate.store`. Тогда чтение в теле `App` не наблюдается, `.tint` приходится переносить внутрь `RootView`, свойство становится IUO. Больше движущихся частей ради того же результата.

**Результат для completion handler.** `send` ничего не возвращает, поэтому `SyncMiddleware.shared.syncNow(reason:)` вызывается напрямую и возвращает `UIBackgroundFetchResult`. Экшен `.sync(.requested)` ведёт в тот же метод: одна реализация, две точки входа, и та, которой нужен ответ, его получает.

**Обратная сторона: `syncNow` не только возвращает, он ещё и диспатчит** — `.sync(.setState)` и обе скобки полного ресинка. На пути экшена `dispatch` ему передан, на пуш-пути его нет: `AppDelegate` зовёт метод, а не стор. Решение — запомненный `dispatch`, который `SyncMiddleware` берёт из последнего прошедшего через него экшена. Прогон, начавшийся раньше, чем такой экшен нашёлся, применит всё правильно, но не подвинет индикатор и не поставит наблюдения на паузу; безопасно это ровно потому, что в том же окне не обработан и `.auth(.set(.authenticated))` — значит наблюдений ещё нет, а показывать индикатор некому.

Три вещи, которые `syncNow` обязан уметь именно на этом пути:

- **Взять `device_id` из keychain, а не из состояния стора.** `send` редьюсит синхронно, но эффекты дренирует в `Task`; между возвратом из `didFinishLaunchingWithOptions` и вызовом `didReceiveRemoteNotification` очередь, скорее всего, уже прошла — но «скорее всего» здесь не годится, а `KeychainService` синхронен и доступен сразу.
- **Дождаться прогона, который его запрос и покроет, если один уже идёт.** Флаг «один прогон за раз» остаётся, и запрос по-прежнему запоминается (`pendingRun`) — меняется только то, что́ на этом пути возвращается. Раньше здесь стоял немедленный `.noData`, «не ждать чужого»; чужой прогон и правда не ответ, но `.noData` — тем более: iOS меряет им бюджет будущих доставок, то есть пуш, принёсший работу, отчитывался как впустую разбудивший. Ждёт **только** этот вызывающий (`reason == .remoteNotification`); у всех остальных результат отбрасывается, и заставлять их ждать нечего.
- **Уложиться в ~30 с.** При уходе в фон с незавершённым прогоном — `beginBackgroundTask`. Ожидание выше ограничено `Constants.Sync.pushResultBudget` (20 с) и по его истечении отвечает `.newData`: пуш назвал ревизию, которой у устройства не было, прогон за ней ещё идёт — из трёх допустимых ответов этот описывает происходящее, а `.noData` был бы единственным, который ещё и наказывается.

**Сверка `r` с курсором живёт внутри прогона, а не в `AppDelegate`.** Подпись — `syncNow(reason:serverRevision:)`; сверка стоит сразу после шага 1 и только на первом круге, потому что курсор читается ровно там, в его собственной транзакции. Прочитать курсор в делегате нельзя, не заведя седьмого метода протокола, — и это было бы чтение, устаревающее прямо в руках: пуш приходит в том числе тогда, когда прогон уже идёт и уже двигает курсор. `AppDelegate` берёт из `userInfo` только `r` (APNs отдаёт числа как `NSNumber`) и передаёт `Int?` — сам `userInfo` не `Sendable` и в `Task` не уезжает.

Сверка отвечает «этой правки у нас ещё нет», а не «мы вообще актуальны»: своё несохранённое к этому моменту не отправлено, и решение о нём принимают триггеры §5.6, а не пуш.

**Ранний выход обязан опустить индикатор.** `.syncing` выставляется до цикла, а `defer` его не снимает — снятие написано явно в конце успешного прогона. Поэтому выход по неактуальному `r` диспатчит `.setState(.idle)` сам; без этого пуш, не принёсший работы, оставлял бы индикатор крутиться до следующего прогона.

### 8.1. Проверка

Это изменение того, где регистрируются сервисы — единственный случай, где зелёная сборка не значит ничего (см. `CLAUDE.md`, раздел Environments). Требуется запуск:

1. Холодный старт: нужный экран, правильный акцент, авторизация проверена.
2. Пуш на свёрнутое приложение — в логе должен быть прогон синхронизации. **Только на устройстве: `xcrun simctl push` этого не проверяет.** Симулятор отказывает в самом запуске — `SBMainWorkspace`, `Disabled ("Unable to launch … because this app doesn't declare the proper UIBackgroundMode")` — при том что `UIBackgroundModes` установленного бандла проверяется `plutil` и `remote-notification` там есть. Отказ снимается, если дописать в копию бандла ещё и `fetch`: приложение тогда действительно поднимается в фоне без сцены, но делегатный колбэк всё равно не приходит — ни в фоне, ни на переднем плане. То есть симулятор не различает «обработчик не вызвался, потому что сломан» и «потому что сюда пуши не ходят», и как признак готовности бесполезен.
3. Отдельно проверить сборкой, что `@StateObject private var store = AppStore.shared` компилируется: обращение к main-actor `static let` в позиции значения по умолчанию — ровно то место, про которое предупреждает комментарий в `combineAppMiddlewares()`. Если Swift 6 его не пропустит, форма такая:

```swift
init() { _store = StateObject(wrappedValue: AppStore.shared) }
```

Проверено: Swift 6 пропускает прямую форму, запасная не понадобилась. Пункты 1 и 3 закрыты, пункт 2 — на устройстве.

**На устройстве понадобится и вход, и внешний отправитель.** `registerForRemoteNotifications()` вызывается только в ветке `.authenticated` (`AuthMiddleware`), так что до входа токена нет и слать некуда; отправителя же до пункта 11 не существует — пуш даёт Push Notifications Console (`apns-push-type: background`, `apns-priority: 5`, окружение Development под debug-подписью). Проверку разумно объединить с приёмкой пункта 11: там тот же пуш идёт уже от сервера, и повторять её дважды незачем.

## 9. Индикатор

`ToolbarItem(placement: .navigationBarLeading)`. Единственный существующий элемент панели — `HomeMenuView` на `.navigationBarTrailing` (`HomeView.swift:97-99`).

| Состояние | Что рисуем | Когда |
|---|---|---|
| `.idle` | **ничего** | нечего отправлять, ничего не идёт |
| `.syncing` | вращение | прогон в полёте либо идёт импорт |
| `.pending` | статичная иконка | есть несохранённое, ждём сеть |
| `.failed` | предупреждение, по тапу объяснение | устойчивый отказ или `failed` импорта |

**Состояние ведёт `SyncMiddleware`, а не запрос к базе.** `.pending` выставляется, когда прогон отложен (backoff, дебаунс при отсутствии сети), и снимается успехом. Отдельного «сколько строк грязных» не считаем: единственное, что это добавило бы, — `.pending` при заведомо недостижимом сервере до первой попытки, а до первой попытки мы этого и не знаем.

**Значения передаются параметрами, не через `@EnvironmentObject`.** Это toolbar content, где окружение достижимо ненадёжно — промах будет крашем, а не неправильным цветом. Читаем в `HomeView`, передаём вниз, ровно как `HomeMenuView(accent:)`.

**Подложка обязательна.** Календарь идёт под навигационной панелью с прозрачным фоном (`transparentNavigationBarBackground()`), глиф оказывается поверх проплывающего дня. До iOS 26 — круг `.ultraThinMaterial` диаметром 36, с iOS 26 система рисует стекло сама. То же, что уже делает `HomeMenuView` (`Circle().fill(.ultraThinMaterial)`, `fallbackDiameter = 36`); без этого индикатор нечитаем поверх полосы месячных.

Никаких алертов. Заголовок `.inline` без текста — появление и исчезновение элемента слева ничего не сдвигает.

**Глифы и подложка — по образцу `HomeMenuView`, один в один.** `.syncing` — системный `ProgressView`, тонированный акцентом: в приложении это уже устоявшийся язык «идёт работа» (`WaitingView`, `RootView`), а не новый глиф, который придётся объяснять отдельно. `.pending` — статичный `arrow.triangle.2.circlepath` тем же акцентом: тот же символ, что и у `.syncing`, различается ровно тем, вращается он или нет, как и требует таблица. `.failed` — `exclamationmark.triangle.fill` с `.symbolRenderingMode(.multicolor)`, то есть системный жёлто-чёрный треугольник, а не ещё один акцентный цвет: третий цвет на этом экране (после двух красных из §9 палитры и оранжевой линии овуляции) означал бы либо конфликтовать с ними, либо подбирать четвёртый оттенок по той же методике, что явно избыточно для предупреждения. Подложка — тот же `Circle().fill(.ultraThinMaterial)` диаметром 36 до iOS 26 и ничего вручную начиная с неё.

**«Объяснение» по тапу на `.failed` — `popover`, не `.alert`.** Ни в одном из двух случаев это не решение, которого ждут от пользователя, а справка на случай, если он всё-таки посмотрел. `.popover` на iPhone сам адаптируется в лист, как уже происходит с `confirmationDialog` в `TagsListView` — вторая реализация того же паттерна, а не новая. Тап и `accessibilityHint` — только на `.failed`; `.pending` и `.syncing` не интерактивны, ровно как в таблице.

**Текстов два, потому что автоматический повтор можно обещать не всегда.** Строка таблицы одна, рисуем одно и то же — различается ровно справка по тапу. Устойчивый отказ синхронизации: ретрай уже запланирован сам, из `handleFailure` (§5.7), и «приложение попробует ещё раз позже» здесь правда. `failed` импорта: клиент при нём ничего не планирует — опрос `.importPoll` следует за нарисованной работой, то есть за `running` (пункт 13), — а сервер держит статус до следующей аутентификации и заново дёргает заявку только на входе (§10.4). Тот же текст здесь обещал бы повтор, которого никто не сделает; второй говорит, что перенести данные из старого приложения не удалось и попытка повторится при следующем входе.

**Какой из двух — по источнику, а не по новому состоянию.** Признак тот же, по которому пункт 13 уже разводит происхождение: `failed` в кэшированном `import_status` (§4.2) пришёл от импорта, всё остальное — из `handleFailure`. Знает об этом только middleware, вывести это в вью неоткуда — поэтому `.failed` несёт `FailureOrigin` (`.syncRun` / `.firebaseImport`), и единственный её читатель — текст popover'а. Ни нового состояния индикатора, ни новой строки в таблице, ни второй ветки рисования: глиф, подложка, тап и `accessibilityLabel` у обоих случаев одни и те же.

**Повтор импорта привязан ко входу, а не к таймеру, намеренно.** Заявку на `failed` забирает любая из трёх точек аутентификации — сорванный сетевой вызов не приговор данным (§10.4); четвёртая точка, `/data/sync`, претендует только на протухший `running` и `failed` не трогает. Расписание означало бы новую выгрузку из Firebase каждые несколько десятков секунд у пользователя, который уже вошёл: чужая сеть и дорогой запрос столько раз, сколько открыто приложение, ради случая, который закрывается ближайшим входом. Данные до него никуда не пропадают — они лежат в Firebase, а календарь пуст ровно настолько, насколько был. Ожидание дешевле расписания, поэтому автоматического повтора здесь спецификация не хочет.

**Появление отложено, исчезновение — нет.** `SyncMiddleware` выставляет `.syncing` в первой же строке `syncNow` — до какого-либо сетевого вызова (§5) — и на быстрой сети снимает его через доли секунды, то есть индикатор мигает без единой реальной причины мигать. `SyncIndicatorView` держит это не через анимацию с задержкой (та лишь красит переход, который всё равно случится), а через второй стейт: `syncState` — то, что прислал middleware, `displayedState` — то, что нарисовано. Переход `.idle → что угодно` не копируется в `displayedState` сразу — вью ждёт `Constants.Sync.indicatorAppearDelayNanoseconds` (700 мс — раунд-трип это TLS, сетевой хоп и транзакция GRDB по обе стороны, а не локальное вычисление, так что «быстрый» прогон и сам по себе может занимать несколько сотен миллисекунд; 400 мс на реальном устройстве оказалось мало и индикатор всё ещё успевал мелькнуть) и берёт актуальное на тот момент значение. Прогон, уложившийся в это окно — обычное дело на быстрой сети, — к моменту срабатывания таймера уже снова `.idle`, и `displayedState` этого перехода не увидит вовсе: индикатор не мигнёт ни одним кадром. Правило одностороннее: `любое-что-то → .idle` и смена между двумя уже нарисованными состояниями (`.syncing → .failed`) применяются немедленно — ждать есть смысл только там, где на экране пока ничего нет и есть что терять, пряча то, что уже показано, дольше, чем оно исчезает само, не даёт ничего. Ключ анимации на `displayedState`, а не `syncState`, потому что решение показывать или нет уже принято к этому месту, здесь только про то, как это выглядит.

**Кроссфейд — это `opacity` на вью постоянного размера, а не вставка/удаление вью.** Первая версия меняла кейсы свитча напрямую (`.idle` — буквальный `EmptyView()` нулевого размера рядом с 36pt подложкой у остальных), рассчитывая на дефолтный `.opacity`-переход SwiftUI между разнотипными вью. Он не сработал: контент индикатора хостится в `UIBarButtonItem`, а изменение *размера* хостящейся там вью навигационный бар просто перекладывает за один кадр — до этого перехода транзакция `.animation` не доходит, сколько её ни навешивай. Теперь `badge { icon }` всегда занимает `fallbackDiameter × fallbackDiameter` — по обе стороны `#available(iOS 26.0, *)` внутри `badge`, тем же `.frame` снаружи, — а `.idle` не убирает вью, а сводит её `opacity` в 0. `allowsHitTesting` и `accessibilityHidden` идут тем же условием: зарезервированный, но невидимый круг не должен ни ловить тапы, ни попадать под VoiceOver.

**Даже так фейд не был виден — понадобился явный `withAnimation`, а не ambient `.animation(value:)`.** Тот же урок, что уже записан для диска выбора в календаре (CLAUDE.md): изменение стейта, пришедшее не из прямого SwiftUI-события — там из очереди диспетча, здесь из пробуждения `Task.sleep` в `reconcile(to:)` — не гарантированно попадает в вью уже завёрнутым в транзакцию, так что модификатор `.animation(value:)`, просто сидящий на дереве вью, эту мутацию не обязательно ловит. `reconcile(to:)` оборачивает каждую свою запись в `displayedState` явным `withAnimation(.easeInOut(duration: fadeDuration))` — вместо одного ambient-модификатора на всё дерево.

## 10. Импорт из Firebase

### 10.1. Форма выгрузки — установленные факты

Проверено на трёх реальных экспортах: 212 циклов, 180 комментариев, 3 тега, 61 привязка тегов к дням.

**Эпоха совпадает.** `day_number` в Firebase — это уже `Daystamp` с той же эпохой 2001-01-01. Проверено на 13 комментариях: день → дата совпадает с датой написания. Часовые пояса не участвуют. `utc_offset: 3` в профиле объясняет почему: старое приложение считало номер дня в зоне пользователя, как `Daystamp` считает в `Calendar.current`.

**`flow_levels` совпадает байт в байт.** Ключ — строка номера дня (`{"6700": 1}`), ровно как `CycleRecord+Queries.swift:172` делает `flowLevels[String(day.rawValue)]`. Значения строго `{1,2,3}` — ровно `DayDetailsView.flowLevelOptions`.

**Ни один ключ `flow_levels` не выходит за `[start, start+period_length−1]`.** Две пользы: механика «логированные выделения удлиняют прогноз» (`lastFlowDay`) на импортированных данных не сработает, и разложенные в отдельную таблицу строки привязываются к своему циклу однозначно (§3.4).

**Овуляция — кэш производной.** 196 из 208 неподтверждённых значений в точности равны `next_start − luteal_phase_length`. Все 12 расхождений приходятся на циклы, за которыми идёт длинный перерыв: значение записывалось, пока следующий цикл был неизвестен, и не пересчитывалось. Максимальная ошибка — 51 день.
Фолбэк старого приложения брал настройку самого пользователя: у третьего пользователя `default_length = 26`, и последний цикл 9356 → 9368 = `start + (26−14)`.
`DayDisplayStateComputer.swift:120-126` считает ту же формулу, всегда актуально.

**`confirmed: true` — настоящие данные.** Встречается у одного пользователя из трёх, 4 цикла; две записи расходятся с производной (+2 и −1).

**`period_length: null` — открытый период.** 8 случаев на трёх пользователей. У третьего — **шесть подряд** в самом начале истории, ритм 25–28 дней, после них ни одного на 69 циклов: человек вбил помнящиеся даты начал, конец периода задним числом не помнят.

**Сироты в `day_tags` — норма.** У двух пользователей из трёх есть ссылки на теги, которых нет в `user_tags`: 22 из 33 и 3 из 28. Тег удалён физически, привязки остались.
На импорте они отбрасываются (§10.2): нарисовать их всё равно нечем, и в старом приложении они были так же невидимы. В живой синхронизации сироты возникают законно — тег удалён на устройстве A, пока B вешало его на день, — там клиент их терпит, и поэтому FK на сервере нет.

**Формат id тега** — base64 от 24-символьного hex, единый у всех пользователей. `UserTagRecord.id` — это `String`, принимает как есть.

**Настройки реально разные:** 28/4/14, 28/5/14, 26/6/14.

**Формат дат непоследователен:** `created_at` в RFC 1123 (`"Tue, 26 Mar 2019 15:47:20 GMT"`), остальные в ISO 8601. Парсер должен уметь оба.

### 10.3. Правила и их цена

**Овуляция без `confirmed` не импортируется.** Непустой `cycle.ovulation` выключает ветку вычисления в `DayDisplayStateComputer` — овуляция замёрзнет и перестанет следовать за настройками и правками стартов циклов. Импорт заморозил бы фертильное окно именно там, где собственный пересчёт ценнее всего.

**`null` → `0`, а не `nil`.** В нашей модели `nil` — soft delete: `fetchCycles()` отфильтрует запись, цикл исчезнет из `cycles`, предыдущий «завладеет» двумя месяцами, номер дня цикла и фертильное окно будут врать.
Асимметрия последствий решает и без доказательства: воскресший цикл виден на экране и удаляется повторно; исчезнувший цикл ломает отображение тихо.

**Сироты `day_tags` отбрасываются.** Фильтр по набору тегов из той же выгрузки. Если после фильтра список дня пуст — строка не создаётся вовсе: пустой `tag_ids = []` в нашей модели значит «пользователь снял все теги», а это другое утверждение.

**`utc_offset` и `last_visit_at` не импортируются, но не потому, что не нужны.** Оба — живое состояние устройства, а не история. Смещение 2019 года снято с телефона, который с тех пор мог переехать; а фиксированное смещение и само по себе неправильный тип — оно ломается на переходе на летнее время и на любой поездке. Правильное представление — идентификатор IANA, который устройство берёт из `TimeZone.current.identifier`. Оба значения приходят живыми в `device` (§4.1).

**Импорт пишет профиль, значит двигает `data_revision`.** `phone_number` и `settings` кладутся через тот же хелпер, что и всё остальное в `users_female` (§4.4, «Правило ревизии профиля»), иначе устройство не вытянет собственные настройки — а это ровно то, ради чего затевался пункт D2.

### 10.4. Процесс

**Триггер** — первая аутентификация пользователя с `firebase_import_status IS NULL`, проверяется во **всех трёх** точках: `migrate`, `verify-code`, `verify-flash-call`. Только `migrate` не хватит: переустановивший приложение и вошедший по телефону идёт мимо него.

**Четвёртая точка — `/data/sync`, и она не про новый импорт, а про брошенный.** Прогон, умерший вместе с процессом, оставляет `running` на строке, а `running` — то, на чём клиент крутит индикатор и, с пункта 13, планирует следующий прогон. То есть он спрашивает снова и снова, и ни один из этих вопросов не может исправить ровно то, о чём спрашивает: до сюда заявка бралась только через вход, а вошедший заново — единственное, чего у такого пользователя может и не случиться. Поэтому ответ, несущий `running` старше пятнадцати минут, дёргает ту же заявку. Решает по-прежнему один условный `UPDATE`: живой прогон свою заявку удерживает, `done` не забирается никогда. Проверка возраста повторена перед вызовом только затем, чтобы здоровый импорт не получал заявку на каждом опросе — а опрос идёт раз в три секунды.

**Возраст заявки клиенту не показывается.** `import_status` едет в ответе (§4.2), `firebase_import_started_at` — нет: это состояние задачи, нужное эндпоинту, чтобы отличить живой прогон от мёртвого, и добавлять его в тело ответа значило бы заводить клиенту решение, которого у него нет.

**Секрет только на сервере.** `MIGRATION_SECRET` в бинарнике приложения — не секрет.

**Через тот же `applyBatch`**, чанками по 200–500 строк (правило §4.4). Телефон затем делает обычный полный sync с `since = 0` — один код-путь вместо двух.

**Статус виден клиенту.** Ответ авторизации не ждёт импорта — но ждёт заявку: один локальный `UPDATE` перед ответом, а выгрузка и запись уходят за него. Иначе первый прогон устройства может обогнать заявку, прочитать `import_status: null`, нарисовать пустой календарь и успокоиться — а пуш в конце импорта придётся на APNs-токен, который ещё не доехал. Окно узкое и открыто ровно на первом входе, то есть на единственном прогоне, ради которого импорт и затевался. `import_status` едет в каждом ответе синхронизации и кэшируется в `sync_state`. При `running` крутим индикатор, а не показываем пустой календарь. `failed` — отдельный статус, он не должен выглядеть как «данных нет».

**Идемпотентность.** После успеха `done` навсегда. Повторный импорт воскресит удалённое.

**Заявка на импорт — один условный `UPDATE`, а не чтение с последующей записью.** Два входа, пришедшие одновременно, читают `NULL` оба, если это две операции, и импорт уходит дважды. Претендовать можно на `NULL`, на `failed` (сорванный сетевой вызов — не приговор данным, следующий вход и есть повод попробовать снова) и на `running` старше пятнадцати минут; на `done` — никогда. Возраст `running` берётся из `firebase_import_started_at`: прогон живёт за ответом авторизации, и умерший вместе с процессом оставил бы `running` навсегда — то есть вечный индикатор на клиенте.

**Статус не пишется через `writeProfile`.** Колонка лежит на `users_female`, но это состояние задачи, а не данные пользователя: клиент читает его из строки на каждом прогоне (§4.2), ревизия ему не нужна, а условную заявку `writeProfile` выразить не умеет.

**«Пользователя нет в Firebase» — это `done`, а не `failed`.** Через тот же триггер идёт каждая регистрация по почте, и ни у одной из них в Firebase ничего нет.

**Коллизия с локальными данными.** Push-before-pull означает, что версия телефона побеждает по совпадающим ключам. Обычно верно — это последнее действие человека. Два известных исключения:

- локально цикл открыт (`period_length = 0`), Firebase знает, что он закончился — локальное победит и период «переоткроется»;
- **локально удалённый цикл воскреснет.** Из-за **D1** снятие отметки начала сегодня удаляет строку физически, надгробия не остаётся, и в push такому удалению нечем поучаствовать. Firebase про этот цикл всё ещё знает, и pull его вернёт. Симптом виден на экране и лечится повторным удалением — уже с надгробием, после решения 7.

## 11. Телефон

**Решение: телефон — вход только для пользователей v2.0. Регистрации по телефону нет и не планируется.**

Это сознательно тупиковая ветка. В будущем существующих телефонных пользователей обяжут привязать почту, после чего вход переедет на email, а телефонный путь отключится. Ничего сверх необходимого для входа старых пользователей здесь строить не надо.

### 11.1. Что берётся от схемы email

Ровно одно: **где искать номер**. Сейчас `check-phone` спрашивает Firebase (`getUIDByPhone`), должен спрашивать свой Postgres — как `check-email` спрашивает `getFemaleByEmail`.

| | email | телефон сейчас | телефон после |
|---|---|---|---|
| Где ищем | Postgres, `getFemaleByEmail` | **Firebase**, `getUIDByPhone` | Postgres, `getFemaleByPhone` |
| Записи нет | регистрация | `404 PHONE_NOT_FOUND` | `404 PHONE_NOT_FOUND` — **без изменений** |
| Подтверждение | код на почту | Flash Call | Flash Call |

Ветка регистрации не переносится.

### 11.2. Курица и яйцо

`getUIDByPhone` делает две вещи: отвечает «такой номер есть» и **резолвит номер в Firebase UID** — первичный ключ `users_female`.

Импорт данных запускается по первой аутентификации, но телефонный вход нуждается в этом соответствии **до** входа. Ленивый импорт не спасает ровно того, кому он нужен.

Поэтому нужен **массовый предперенос индекса «номер → UID»** для всех пользователей, отдельно от переноса данных и до отключения Firebase. Только личность — id и номер; цикловые данные едут лениво.

Цена невыполнения — не потеря данных, а невозможность войти: неперенесённый пользователь получит `404`, тот же ответ, что и сегодня. Блокер отключения Firebase, но не риск для данных.

### 11.3. Три ступени `check-phone` на время перехода

```
1. Postgres → нашли  → Flash Call → вход
2. не нашли → Firebase getUIDByPhone
     нашли → v2.0: создать строку с ЕГО UID + номером → Flash Call → вход
3. нет нигде → 404 PHONE_NOT_FOUND (как сегодня)
```

Ступень 2 — переключение без дня X: она же и дозаписывает то, что массовый перенос пропустил. После отключения Firebase исчезает, и остаются 1 и 3.

**Создание строки переезжает из `verify-flash-call` в `check-phone`.** Сегодня пользователь создаётся на шаге верификации, потому что Firebase ответил, а в Postgres его ещё нет. После перехода он создаётся на ступени 2, до звонка — и к моменту `verify-flash-call` уже существует. Ветка создания в `verify-flash-call` удаляется целиком: если сессия ведёт к несуществующему пользователю, это ошибка, а не повод завести аккаунт.

### 11.4. Сервер

- `users_female.phone_number TEXT UNIQUE` — E.164, nullable (у email-пользователей его нет);
- `getFemaleByPhone` — нового метода в `female.js` нет, добавить рядом с `getFemaleByEmail`;
- `getFemaleById` расширить: сегодня он не выбирает `phone_number` (`female.js:44`), а профиль в `/data/sync` его отдаёт;
- **`createFemale` чинится (D5)** — обязана уважать переданный `id`, иначе бэкфилл на ступени 2 создаст строку со случайным ключом. Вызов из `verify-flash-call` при этом удаляется, так что сам симптом D5 исчезает вместе с ним;
- **обработчик `23505` в `createFemale` (`female.js:87`) перестаёт быть верным**: он возвращает `Email already in use` на любое нарушение уникальности, а с появлением `phone_number UNIQUE` их станет два. Различать по `error.constraint`;
- **импорт** заполняет `phone_number`, если пусто — через хелпер ревизии профиля (§4.4).

**Код звонка ограничен тремя попытками** — сделано, миграция `005_flash_call_attempts.sql`. Код Flash Call — четыре цифры, десять тысяч вариантов. Сессия жила десять минут, неудачная проверка не меняла в строке ничего, и единственным, что стояло между известным `requestId` и перебором, было поведение Lancktele: не наше, нигде не зафиксированное и в любой момент способное измениться. `flash_call_sessions.attempts` считает неудачи, на третьей сессия сжигается.

**Сжигается через `expires_at = now()`, а не `DELETE`.** Строка сессии — ещё и улика лимита частоты: `checkRateLimit` считает сессии, попавшие в окно. Сессия, исчезающая ровно в тот момент, когда исчерпана, не стоила бы перебирающему ничего — следующая заявка начинала бы с чистого счёта. `getUserByRequestId` фильтрует по `expires_at`, так что годиться для аутентификации сожжённая сессия перестаёт тем же оператором, каким сжигается.

**Сборщик перестал возвращать квоту.** `cleanupExpiredSessions` удалял всё, что уже истекло, — то есть ровно те строки, по которым считается лимит. Ежечасный cron тихо возвращал каждому пользователю его пять звонков. Срок хранения теперь выводится из окна лимита (`SESSION_RETENTION_MINUTES = RATE_LIMIT_WINDOW_MINUTES`) одним значением, чтобы два этих числа не разъехались молча.

**`retryAfter` считается от освобождения слота**, а не объявляет полные тридцать минут тому, у кого двадцать девять из них уже позади.

**Ответ на исчерпанной сессии — `429 TOO_MANY_ATTEMPTS`**, и `data.remainingAttempts` едет в каждом отказе по коду. Клиента это не ломает и правки не требует: §5.7 уже читает 429 по `Retry-After`, а текст ошибки экраны входа показывают серверный — как сегодня с `RATE_LIMITED` из `check-phone`.

**Что НЕ меняется**, вопреки тому, что понадобилось бы для регистрации:

| | Почему не трогаем |
|---|---|
| `flash_call_sessions.user_id` | Известен до звонка на всех трёх ступенях — nullable не нужен. Колонка `attempts` рядом — другое дело, см. выше |
| `flashCall.checkRateLimit(userId)` | Ключ на `user_id` работает: он резолвится на строке 224 `check-phone`, до `requestFlashCall` на 243. Изменился не ключ, а срок жизни строк, по которым он считает |
| Клиент | `PhoneAuthState`, ветка в `AuthMiddleware.swift:120-146`, `AuthenticationError.phoneNotRegistered` — всё остаётся |

Стоимость звонков тоже остаётся ограниченной: Flash Call инициируется только для номеров, которые уже есть в базе, — а теперь ещё и бюджетом на адрес (§16), потому что «есть в базе» проверяется до лимита и само по себе является ответом, за которым можно прийти.

Теперь прогон завершается `SyncState(afterImport:)` — `running` даёт `.syncing`, `failed` даёт `.failed`, всё остальное `.idle`.     **Статус несёт прогон, а не последний ответ.** Ответ может его не назвать, а `applySync` кладёт колонку через `COALESCE`, то есть молчание значит «как было». Поэтому значение переносится между раундами: берётся из `sync_state` в начале каждого и перезаписывается ответом, только если тот его назвал.
    **Интерпретация — в одном месте, хранение — строкой.** `running`/`failed` разбираются в `SyncState.init(afterImport:)` и больше нигде; на проводе и в базе статус остаётся `String`, потому что незнакомое этой сборке значение должно пережить круг, а не быть переписанным в понятное ей.
    **Прогон, закончившийся `running`, спрашивает снова сам.** Пуш в конце импорта — подсказка, и ровно на том единственном прогоне, который здесь важен, эта подсказка может промахнуться: импорт стартует в момент авторизации, когда APNs-токен этого устройства ещё едет на сервер, — и `sendSyncToUser` уйдёт в пустой список токенов. Это не про разрешения (silent push их не требует, а `registerForRemoteNotifications` зовётся безусловно) и не про бюджет APNs (тот про пробуждение усыплённого приложения, а не про работающее) — это гонка первого входа, то есть в точности случай импорта. Данные при промахе не теряются, `import_status` едет в каждом ответе; теряется только повод спросить, и календарь стоит пустым под крутящимся индикатором до ближайшего выхода из фона.
    Поэтому `SyncMiddleware` планирует следующий прогон (`.importPoll`, `minImportPoll` 3 с с удвоением до `maxImportPoll` 60 с). Это не страховка от APNs, а `has_more` между прогонами вместо `has_more` внутри одного: сервер сказал, что не закончил, — клиент спрашивает снова, ровно как на всякий другой незакрытый ответ в §5. **Условием стоит нарисованное состояние, а не строка статуса:** прогон, закончившийся показом работы, и есть прогон с неоконченным импортом — так говорит таблица §9, — и `running` остаётся написанным в одном месте вместо двух.
    **Вечный `running` закрыт со стороны сервера.** Опрос из §13 держится на том, что `running` когда-нибудь сменится, а прогон, умерший вместе с процессом, его не сменит: пятнадцатиминутная заявка была, а забирать её было некому — все три точки её вызова суть входы. Теперь заявку дёргает и `/data/sync` (§10.4, четвёртая точка), и это правка сервера, а не клиента: клиент ведёт себя ровно как условлено — сервер сказал «не закончил», клиент спросил снова, — врал сервер. Заодно точки авторизации ждут заявку перед ответом, чтобы первый прогон устройства не обогнал её и не увидел `null` вместо `running`.
    **Отложенный вопрос и начатая работа — разные задачи.** Все три планировщика (`scheduleImportPoll`, `scheduleDebouncedRun`, `scheduleRetry`) досиживают свой сон и передают прогон в `start(reason:)`, а не зовут `syncNow` внутри собственной задачи. Иначе хэндл переживает отсрочку и начинает называть работу — а его отменяет каждый, кто планирует следующее. У опроса это било в упор: `syncNow` открывается снятием `importPollTask`, то есть поллинговый прогон отменял сам себя, первый же `await` бросал `CancellationError`, и §5.7 рисовала `.failed(.syncRun)` — треугольник ровно на импорте, ради которого опрос и написан, плюс подмена интервала опроса ретрайным backoff. У дебаунса тот же дефект достижим обычной работой: правка дня, пришедшая пока предыдущий прогон в сети, обрывала его запрос. Останавливать прогон, который не должен доработать, умеет `sessionEpoch` (§6), и только он. Сам отменённый прогон больше не ошибка — см. новую строку §5.7: индикатор оставляет тот, кто отменил.

    **Таймер и интервал опроса отдельны от `retryTask`/`backoff`.** Форма у них одна («один будущий прогон, не больше одного отложенного»), но ретрай следует за отказом, а опрос — за успехом: общий интервал позволил бы медленному импорту раздуть backoff, которым меряется настоящий обрыв, и обнулять его каждым нормально вернувшимся ответом. Новый прогон снимает отложенный вопрос, но **не** трогает интервал — иначе удвоение обнулялось бы на каждом опросе, и зависший импорт спрашивался бы каждые три секунды всё время, пока приложение открыто.

## 13. Отвергнутые варианты

| Что | Почему отвергнуто |
|---|---|
| Метка времени вместо счётчика ревизий | Часы устройства и сервера, `TIMESTAMP` без таймзоны, совпадения меток внутри одной транзакции, необходимость `>=` с дедупликацией |
| Курсор как `MAX(updated_at)` по таблицам | Производное значение; после локальной правки самой свежей строки отъезжает назад, при частично применённом батче врёт. `lastSyncTimestamp()` — его единственная реализация, удаляется в пункте 5 |
| `next_cursor` = максимум по возвращённым строкам | Теряет хвост усечённой таблицы, если другая таблица дотянулась до бо́льших ревизий (§4.4). Правило размера транзакции этого не ловит: разрез между таблицами, а не внутри ревизии |
| `REPEATABLE READ` вместо блокировки строки пользователя | Даёт тот же снимок, но требует цикла повторов на `serialization_failure`; блокировка строки на пишущем пути и так уже есть и делает оба пути одинаковыми (§4.3) |
| Булев `is_dirty` | Теряет правку, случившуюся пока запрос в полёте (§5.4) |
| Отдельный запрос за `sent_max` | Между ним и чтением строк проходит локальная запись, и её флаг снимается как отправленный (§5.4) |
| Проверка владельца только в ответе синхронизации | Стоит после push: база предыдущего пользователя успевает уехать в чужой аккаунт. Основная проверка — при входе, где `user_id` уже известен (§6) |
| `server_revision` в каждой таблице | Была нужна для выбора мягкого/физического удаления; удаление теперь всегда мягкое, конфликты last-write-wins, курсор глобальный — читателей не осталось |
| `batch_revision` в ответе | Клиент снимает флаги по `dirty_seq`, курсор берёт из `next_cursor`; значение внутреннее для сервера |
| `user_devices.last_synced_revision` | Кому слать пуш решает `device_id != caller`; отстающее устройство отсеет себя по `r` из payload |
| `NWPathMonitor` | Backoff с потолком в минуту закрывает тот же случай |
| Раздельные push/pull эндпоинты | Порядок «push раньше pull» становится соглашением, а не конструкцией |
| Слияние `flow_levels` на сервере по ключам | Не отличает «не трогал день 5» от «стёр день 5»: замена это выражает, слияние нет. Потребовало бы надгробий на каждый ключ внутри JSON и поключевых историй под одной ревизией строки — та же сложность, что у отдельной таблицы, без её ясности |
| Каскадное удаление выделений вместе с циклом | Ломает «удаление = одна строка» и требует, чтобы сервер знал правило каскада. Выделения — наблюдение о дне, они переживают правку учёта (§3.4) |
| Стор в `AppDelegate` | Чтение в теле `App` не наблюдается, `.tint` надо переносить, свойство становится IUO (§8) |
| Создание таблиц из кода приложения | Пул на 10 соединений и `touch ../reload` — не место для DDL; README утверждал обратное и был неправ (§3.5) |
| `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` | Уже пробовали, откатили — см. `CLAUDE.md`, Environments |

**Не отвергнуто, а отложено:** `full_resync_required`. Раньше он значился здесь с обоснованием «нужен только при чистке tombstone'ов; не чистим». Обоснование неполное: он нужен ещё и для эволюции набора таблиц (§4.6), а добавить его задним числом нельзя — клиент, который его не читает, читать не начнёт. Поле заводится сразу, сервер сегодня не выставляет его никогда.

## 14. Тесты

Режимы отказа этой работы тихие: потерянные строки не дают ни ошибки, ни записи в лог — они просто не приезжают, и замечают это через недели. Ни в одном из двух репозиториев тестов сейчас нет: `npm test` в `redcalendar-api` — это `eslint`, iOS-таргета для тестов не существует.

Минимум, без которого пункт 3 не считается сделанным:

**Правило страницы (§4.4)** — чистая функция от «что вернула каждая таблица» к `(next_cursor, has_more, что отдать)`. Она и должна быть чистой функцией, отдельно от SQL, ровно чтобы её можно было проверить. Случаи:

1. ничего не усечено → максимум, `has_more = false`;
2. усечена одна таблица, другая дотянулась выше → курсор по усечённой, строки выше выброшены (пример из §4.4);
3. усечены две → минимум из двух;
4. страница режет ревизию пополам → спуск к предыдущей отличной;
5. одна ревизия больше страницы → отдаётся целиком, `has_more = true`, курсор двинулся;
6. `R` выделен, строк не вернулось вовсе → курсор = `R`.

**Правило снимка (§4.3)** — интеграционно, на реальном Postgres: два параллельных прогона одного пользователя, у одного пустые `changes`. Без `FOR SHARE` тест краснеет; это и есть его смысл.

**Применение на клиенте (§5.1, шаг 7)** — четыре комбинации «строка грязная/чистая × пришла в `changes`/в `rejected`», плюс правка в полёте (`dirty_seq > sent_max`), плюс pull-only прогон при поголовно грязной базе: флаги обязаны остаться, а серверные строки по чужим ключам — примениться. Это на iOS, и тестового таргета там нет; пока он не появится, эти шесть случаев проверяются руками по чек-листу и в код-ревью. Заводить таргет ради них — отдельное решение, здесь не принимается.

Инфраструктура на сервере — `node --test`, встроенный в Node 18+; CI уже на 24.1.0, новых зависимостей не нужно. Файлы в `app/test/`, `"test": "npm run lint && node --test"` в `package.json` — и GitHub-workflow (`netangels-deploy.yml`, общий для production и staging) начинает их гонять без единой правки (проверено: без единого теста раннер выходит с нулём, так что пункт можно поставить до того, как тесты написаны).

**Как разложено.** `sync.test.js` — пишущий путь (пункт 2); `sync-page.test.js` — правило страницы; `sync-validation.test.js` — §4.5; `sync-run.test.js` — выбор формы шага 2 на подставном клиенте, без базы; `sync-live.test.js` — правило снимка и прогон целиком, на живом Postgres. Дальше, от пункта 13: `firebase-import-map.test.js` — правила §10.2 и §10.3 по одному на тест; `firebase-import-run.test.js` — заявка, статусы и чанки на подставном клиенте, без базы и без Firebase. От пункта 17: `rate-limit.test.js` — окно, изоляция адресов и подметание; `verification-code.test.js` — предел попыток на строке без `maxAttempts` и равномерность кода; `logging-redaction.test.js` — маскирование; `email-render.test.js` — экранирование шаблонов. От пункта 18: `account-deletion.test.js` — заявка, восстановление и стирание (§17.11).

Пункт 17 стоит здесь особняком: тесты к нему написаны не потому, что этого требовал план, а потому, что до него весь `auth` не был покрыт ничем — и три из четырёх дефектов, которые он чинит, дожили именно там, где никто не смотрел.

**Живые тесты пропускаются, если база не настроена** (`DBHOST`/`DBNAME`/`DBUSER`), и это не смягчение требования, а условие того, чтобы оно вообще исполнялось: красный CI, чинить который нечем, отключают через неделю. Пропуск видно в выводе (`skipped 1`) — молчаливо исчезнувший тест был бы хуже отсутствующего. Прогон против staging — тем же окружением, каким ходит приложение; тесты заводят собственного пользователя и удаляют его за собой.

## 15. За рамками этой спецификации

**Уведомления — расписание всё ещё отдельное проектирование, но согласие уже спрашивается.** Ни расписания, ни локальных уведомлений в новом стеке по-прежнему нет: таблица `notification_schedule` есть в базе, кода к ней нет; `push.js` умеет только `alert`. В v2.0 это работало на `utc_offset` (9 утра по местному) и `last_visit_at` (не будить недавно заходившего), и здесь под то же самое заложены `user_devices.timezone` и `last_seen_at` (§4.1) — подготовка, а не реализация.

Что появилось на клиенте — **два независимых ответа на вопрос «придёт ли уведомление»**, и путать их нельзя:

| Ответ | Чей | Где живёт |
|---|---|---|
| Хочет ли этого аккаунт | пользователя, общий для всех его устройств | `settings.notifications.muted` в профиле (§4.4) |
| Разрешил ли этот телефон | iOS, и только iOS | `UNUserNotificationCenter`, `NotificationState.pushPermissionState` |

Ключ — `muted`, а не «enabled»: именно его писала v2.0, и импорт перенёс его дословно (§10.2). Заводить второй ключ на тот же вопрос значило бы держать на аккаунте два ответа без признака, какой из них текущий. Пишется он тем же путём, что и длина цикла: `.data(.setNotificationsEnabled)` → `DatabaseMiddleware` → `DatabaseService.updateNotificationsMuted` → мерж в `settings_json` → `dirty_seq` → `changes.profile`. Инверсия «enabled → muted» происходит ровно на одной границе — в мидлваре, — чтобы выше неё всё говорило в ту же сторону, что и переключатель на экране.

**Устройство, которому iOS отказала, не трогает настройку аккаунта.** Это разные ответы: на другом телефоне того же человека уведомления по-прежнему разрешены и заслужены. Переключатель в `SettingsView` в этом случае недоступен и нарисован выключенным (это правда про *этот* телефон), под ним — объяснение и ссылка в системные настройки; сама же настройка аккаунта остаётся какой была.

**Системное разрешение спрашивается по состоянию, а не по моменту входа.** Раньше это делал `AuthMiddleware` на `.authenticated` — единственный момент, когда приложение знает меньше всего: профиль возвращающегося пользователя ещё не подтянут, так что вопрос, который iOS разрешает задать один раз за установку, доставался и тем, кто выключил уведомления на другом устройстве. Теперь условие — два поля состояния (`preference == .enabled` и `pushPermissionState == .notAsked`), и `PushNotificationsMiddleware` проверяет его при изменении любого из них. Отсюда бесплатно получаются все сценарии: включение тумблера в настройках, ответ на онбординге, включение на другом устройстве (условие сработает на пуле профиля) и «версия приложения ещё не спрашивала» (сработает на первом же чтении профиля).

Четыре вещи, которые в этом правиле несущие:

1. **«Профиль ещё не читался» — не то же самое, что «в профиле ничего не сказано».** Оба выглядят как отсутствующий `muted`, но означают противоположное: первое — возвращающийся пользователь, у которого настройка может быть выключена, и спрашивать его нельзя; второе — любой аккаунт, приехавший из v2.0, где молчание всегда означало «включено». Отсюда `NotificationPreference` с тремя случаями, а не `Bool?`.
2. **Алерт не показывается поверх онбординга.** Вход запускает недебаунсенный прогон, тот подтягивает профиль, записанный сервером при регистрации, — и условие выполняется ровно на том экране, который сам спрашивает про уведомления, до того как человек тронул тумблер. Третье условие правила — `isFreshRegistration == false`. Перепроверки на `.completedRegistrationOnboarding` при этом нет: этот экшен отправляется сразу за записью тумблера, которая ещё не вернулась через наблюдение, так что в состоянии в этот момент лежит *подтянутая* настройка — и тот, кто только что выключил уведомления, всё равно получил бы запрос.
3. **Алерт не показывается в фоне.** Тихий пуш будит приложение, прогон синхронизации подтягивает профиль — и условие выполняется там, где на алерт некому смотреть, а он один на установку. Запрос пропускается, а `.checkPermissionState` на каждом возврате в активное состояние приводит его обратно.
4. **Регистрация в APNs не зависит от ответа.** Токен несёт тихий пуш синхронизации (§7, §8), который нужен и заглушённому аккаунту, поэтому `registerForRemoteNotifications` вызывается на каждом входе независимо от `muted`.

**Серверная половина не сделана.** Планировщик (когда он появится) обязан читать `settings.notifications.muted` перед `sendAlertToUser` — клиент этот флаг теперь пишет и синхронизирует, но никто на сервере его пока не смотрит. `sendSyncToUser` под это правило не подпадает: тихий пуш — не уведомление.

**Редактирование профиля с устройства — производитель появился.** `SettingsView` редактирует длину цикла и длительность месячных: `.data(.setCycleLength/.setPeriodLength)` → `DatabaseMiddleware` → `DatabaseService.updateCycleSettings` → `user_profile.dirty_seq` → `changes.profile`. Экран дебаунсит правку так же, как редактор комментария, — промежуточные значения удерживаемого степпера стоят ровно столько же, сколько промежуточные значения недопечатанного комментария, и одного намерения не должно хватать на шестьдесят две транзакции. Имя с устройства по-прежнему не редактируется. Раздел остаётся здесь потому, что описывает то, что заложенный путь потребовал при первом же реальном использовании.

Подстеленное место сработало: `settings` хранятся в `user_profile.settings_json` тем JSON, каким их прислал сервер, и локальная правка **мержится** в него (`JSONValue.setting(_:to:)`), а не пересобирается из `UserSettings`. Пересборка выбросила бы ключ, которого эта сборка не знает, и первый же push стёр бы его на сервере для всех устройств — сервер пишет колонку целиком (`writeProfile`: `settings = $n::jsonb`).

Три вещи пришлось починить ровно в тот момент, когда путь перестал быть пустым:

1. **`SyncProfilePush` больше не отправляет поле, которое не редактирует.** Сервер разбирает `changes.profile` по `hasOwnProperty` (`pickProfileFields`, §4.5): `name: null` — «стереть имя», отсутствующий `name` — «не трогать». Пока производителя не было, безусловная отправка обоих ключей ничего не стоила; с производителем устройство, у которого профиль ещё не подтянут, отправило бы `null` и стёрло имя, данное при регистрации, — на сервере, для всех устройств. В типе это записано двойным optional (`String??`): `nil` — «не редактируется», `.some(nil)` — «стереть».
2. **Грязный профиль придерживает только половину строки.** Шаг 7.1 применяет `user_id`, `email` и `phone_number` независимо от флага — их устройство не пишет вообще (§4.4, правило личности), — и придерживает только `name` и `settings`. Пропуск строки целиком, как у любой таблицы, оставил бы без личности устройство, которое поправило настройки до того, как профиль впервые приехал: курсор уйдёт за эту ревизию, и `profile_revision > since` больше не выполнится никогда.
3. **`updateCycleSettings` — единственный локальный писатель `user_profile` и единственное, кроме pull, что заводит его строку.** До сих пор её заводила только синхронизация (§3.1), так что у вошедшего пользователя без единого успешного прогона строки для правки нет. Заведённая локально несёт `user_id` из `sync_state`, если он там есть, и не несёт никакой личности, если его нет: заполнить её — дело ближайшего pull. Из-за этого строка приезжает в стор **двумя** экшенами: `.setUserProfile` везёт личность, `.setCycleSettings` — то, чем рисует календарь. Свёрнутые в один, они означали бы, что правка, сделанная до первого прогона, возвращается из наблюдения как `nil`, и только что выбранное число прыгает обратно к фолбэку прямо на экране.

Одна граница осталась намеренно неподвижной. Экран показывает значение, заклампленное в `Constants.Cycle`, но **записывает только по тапу**. `settings` проверяются на форму, а не на содержимое (§4.5), поэтому в колонке может лежать любое число, которое туда когда-либо записал клиент; значение, которое эта сборка заклампила бы, всё равно остаётся выбором того человека, и записывать вместо него нашу версию — не наше дело. Запись «на появление экрана» сделала бы ровно это. (В боевых профилях сегодня 26–29, внутри границ. Число 19 в таблице §4.5 — это наблюдаемый *интервал между началами циклов*, то есть `CycleRecord`, а не эта настройка.)

**Открытый вопрос — один:**

**`secret_key` в `README.md`** репозитория `redcalendar-api` лежал открытым текстом, и, судя по всему, это боевое значение `MIGRATION_SECRET`.

Из рабочего дерева он убран, но **в истории git остался**: `git log -S` находит его и в `README.md`, и в `40f30c5`. Удаление строки историю не переписывает, а `origin` — `github.com/artembolotov/redcalendar-api`. Если репозиторий публичный, значение надо считать раскрытым и ротировать; закрывать вопрос по факту исчезновения строки из рабочего дерева нельзя. Ротация здесь дешёвая: `MIGRATION_SECRET` читается из окружения в двух местах (`check-phone.js`, `firebase-import.js`) и должен совпасть с тем, что проверяет Cloud Function.

## 16. Ограничение частоты запросов

Появилось разбором ревью (§12, пункт 17), а не пунктом плана, и закрывает вопрос, которого никто не задавал. Лимиты, которые были, отвечают на «сколько можно сделать одному пользователю»: коды на адрес почты, звонки на `user_id` (§11.4). «Сколько может попробовать один источник» не спрашивал никто — а именно это спрашивает перебор. `check-phone` отвечает, был ли номер пользователем v2.0, то есть является оракулом; и каждый прошедший запрос, который нашёл номер, вдобавок заказывает платный звонок.

`services/rate-limit.js`, фиксированное окно, счётчики в памяти процесса.

| Эндпоинт | Бюджет на адрес | Переменная окружения |
|---|---|---|
| `/auth/check-email`, `/auth/check-phone` | 30 / 15 мин | `RATE_LIMIT_AUTH_SEND_CODE_MAX` |
| `/auth/verify-code`, `/auth/verify-flash-call` | 60 / 15 мин | `RATE_LIMIT_AUTH_VERIFY_MAX` |
| `/auth/migrate`, `/auth/apns-token`, `/auth/logout`, `/auth/account` | 120 / 15 мин | `RATE_LIMIT_AUTH_SESSION_MAX` |
| `/data/sync` | 600 / 5 мин | `RATE_LIMIT_DATA_SYNC_MAX` |

Отказ — `429`, тело обычной формы (`{success, error: "RATE_LIMITED", message, retryAfter, timestamp}`), заголовок `Retry-After`. На клиенте это уже описанная строка §5.7, новой ветки не требуется.

**Числа взяты с большим запасом, и это не осторожность, а необходимость: адрес — не человек.** Мобильные операторы держат сотни живых пользователей за одним адресом CGNAT, и лимит, настроенный так, будто на IP приходится один пользователь, выключает вход целой сети. Поэтому каждый перенастраивается переменной окружения — цифру, которая может оказаться неверной при десятикратном трафике, нельзя держать только в коде.

**В памяти — сознательно, и цена названа здесь, а не обнаружена потом.** API работает одним процессом за прокси хостинга; общее хранилище было бы второй движущейся частью, стерегущей трафик одного процесса. Счётчики обнуляются на каждом рестарте и деплое. Если процесс когда-нибудь запустят во втором экземпляре, заменять надо этот модуль, а не места вызова, — ради чего он и отделён от них.

**Окно фиксированное, а не скользящее.** На стыке двух окон можно потратить двойной бюджет. Против перебора, где интересна цифра «запросов в час», множитель два не меняет ничего, а скользящий журнал стоил бы массива отметок времени на каждый адрес.

**`trust proxy` — несущая строка, а не гигиена.** Приложение отдаётся через обратный прокси хостинга, поэтому адрес на сокете всегда принадлежит прокси. Без `app.set('trust proxy', 1)` в `hello.js` `req.ip` — это `127.0.0.1` для всего мира, и весь интернет попадает в одно ведро. Один хоп, а не `true`: доверие всей цепочке `X-Forwarded-For` позволяет подставить любой адрес и выбирать себе свежее ведро на каждый запрос — это хуже отсутствия лимита, потому что похоже на лимит.

**Чего этот раздел не делает.** Он не заменяет ни лимита на адресат, ни предела попыток: те отвечают за то, сколько можно сделать конкретному человеку, и остаются единственным, что работает, когда источников много. Бюджет на адрес — верхняя граница для одного источника, и только.

## 17. Удаление аккаунта

**Решение: отложенное удаление без кода подтверждения.** Заявка снимает все сессии и метит строку пользователя; через четырнадцать дней крон уничтожает её физически; вход в течение этого срока отменяет удаление.

| # | Вопрос | Решение |
|---|---|---|
| 1 | Подтверждение | Экран приложения. Кода из письма нет — §17.1 |
| 2 | Данные | Мягкое удаление: `users_female.deleted_at`, физическое стирание по крону |
| 3 | Срок покоя | 14 дней. Потолок — 30 (152-ФЗ); `ACCOUNT_DELETION_GRACE_DAYS` выше потолка не пускает |
| 4 | Сессии | Все `user_devices` пользователя удаляются в транзакции заявки |
| 5 | Восстановление | Обычный вход; сервер отвечает `restored: true` |
| 6 | Что остаётся навсегда | Только UID в `deleted_users` — §17.5 |
| 7 | Эндпоинт | `DELETE /auth/account`, сессионный бюджет (§16) |

### 17.1. Почему нет кода из письма

Модель угрозы у кода одна: чужой человек с разблокированным телефоном. Но почта у такого человека обычно на этом же телефоне, и код он получит. Стоит же он нового `purpose` в `verification_codes`, второго эндпоинта отправки, шаблона письма, своих лимитов — а для телефонных пользователей ещё и платного Flash Call, при том что у части из них почты нет вообще (§11).

Главное: **код проверяет личность в неподходящий момент.** От необратимой потери данных защищает не подтверждение до удаления, а возможность отменить его после. Отсрочка эту проверку делает сама и бесплатно: чтобы восстановить аккаунт, надо войти — то есть получить код на почту или принять звонок. Тот же код, но в точке, где он действительно что-то решает.

Что требуется вместо него: деструктивный лист в приложении с прямым текстом — что удаляется, когда становится окончательным и что вход до этой даты всё вернёт. Это же и то, чего ждёт Apple по 5.1.1(v): удаление инициируется в приложении и доводится до конца, отсрочка допустима, если о ней сказано.

Побочное следствие, приятное: ревьюер App Store, удаливший тестовый аккаунт (`TEST_ACCOUNT_EMAIL`), не ломает его насовсем — следующий вход по фиксированному коду возвращает аккаунт целиком.

### 17.2. Почему отсрочка, и почему четырнадцать дней

Три причины, и первая — не главная:

1. **Опечатка пальцем необратима.** Цикловая история за годы — не то, что достают из бэкапа хостинга поштучно.
2. **152-ФЗ даёт ровно тридцать дней** с момента отзыва согласия на уничтожение данных. Окно в тридцать не оставляет запаса на прогон крона, которого не случилось; четырнадцать лежат внутри с запасом и давно за пределами срока, когда ошибочное удаление ещё не заметили.
3. **Мгновенное удаление всё равно не было бы полным.** Данные v2.0 лежат в Firebase, и стирание нашей копии их не трогает (§17.5).

Число берётся из окружения (`ACCOUNT_DELETION_GRACE_DAYS`), как и всякое другое, которое может оказаться неверным (§16), но **только вниз**: значение вне 1..30 — это не предпочтение, а ошибка конфигурации, и безопасное её прочтение — умолчание, о чём пишется `WARN`.

### 17.3. Заявка

`DELETE /auth/account`, `Authorization: Bearer <device_id>`, рядом с `/auth/logout` и под тем же сессионным бюджетом. Одна транзакция (`services/account.js`, `requestDeletion`):

```
1. UPDATE users_female SET deleted_at = now() WHERE id = $1 AND deleted_at IS NULL
2. DELETE FROM user_devices          WHERE user_id = $1   -- все сессии, включая эту
3. DELETE FROM flash_call_sessions   WHERE user_id = $1   -- FK нет, каскад не сработает
4. DELETE FROM notification_schedule WHERE user_id = $1
5. DELETE FROM verification_codes    WHERE email   = $2   -- ключ по почте, не по id
```

**Шаг 2 несёт больше, чем «выйти на всех устройствах». У удаляемого аккаунта не остаётся ни одного устройства — значит `/data/sync` до него не дотягивается вообще.** Весь путь синхронизации об удалении знать не обязан: `verifyDevice` не проходит, а дальше проверять нечего. Это тот же приём, каким §4.3 делает шесть `SELECT`ов одним снимком: свойство обеспечивается конструкцией, а не соглашением помнить про фильтр в каждом новом запросе.

**Но одно место фильтр всё же требует — сам `verifyDevice`.** «Устройств не остаётся» верно для заявки и неверно для гонки с ней: `createDevice` проверяет существование пользователя и вставляет устройство двумя отдельными операторами, а `migrateUser` читает строку без блокировки. Заявка, закоммиченная между проверкой и вставкой, оставляет сессию на помеченном аккаунте — и та работает весь срок покоя, пока крон не унесёт данные из-под живого устройства. Окно — миллисекунды, но закрывается оно одной строкой `AND uf.deleted_at IS NULL` в запросе `verifyDevice`, через который проходит каждый авторизованный маршрут. Это то самое «одно место» из §17.10, а не фильтр, размазанный по десяти.

**Шаг 3 — не гигиена.** Сессия Flash Call живёт десять минут и ведёт прямо к `createDevice` (`verify-flash-call.js`); оставленная, она выдаёт устройство на удалённый аккаунт через минуту после удаления.

**Шаг 5 — потому что коды привязаны к адресу, а не к пользователю** (`services/verification.js`), и каскад до них не достаёт. Живой код — это дорога обратно в аккаунт, который только что попросил его закрыть.

**Заявка идемпотентна.** Повторная находит метку уже стоящей и всё равно проходит по четырём таблицам: первый вызов мог умереть между `UPDATE` и `DELETE`, а строка устройства, пережившая заявку, — единственное, чего эта функция оставить не имеет права.

**`deleted_at` не идёт через `writeProfile`,** хотя колонка лежит на `users_female` (§4.4, правило ревизии профиля). Правило существует ради того, чтобы устройство узнало; здесь узнавать некому — устройств у аккаунта не остаётся в той же транзакции, а то, которое войдёт потом, начинает с курсора 0 на стёртой локальной базе (§6) и вытягивает профиль при любой его ревизии. Тот же довод, по которому вне правила стоит `firebase_import_status` (§10.4).

### 17.4. Восстановление

Вход в течение срока покоя снимает метку — и больше ничего не делает: данные не трогались, ревизии не двигались, так что аккаунт возвращается ровно таким, каким был. Три точки входа, все три обязаны:

| Путь | Что делает |
|---|---|
| `verify-code` | `getFemaleByEmail(..., { includeDeleted: true })`, снять метку **до** `createDevice`, в ответе `restored: true` |
| `verify-flash-call` | То же по `getFemaleById`; без `includeDeleted` строка невидима, а второй такой не создать — UID первичный ключ, и вход кончился бы `23505` под видом «Email already in use» |
| `migrate` | Снятие метки внутри транзакции `migrateUser`, до вставки устройства |

`check-email` отвечает `isRestore: true`, чтобы экран ввода кода мог сказать, что вход вернёт аккаунт, а не заведёт новый. Клиент, который поле игнорирует, видит обычный вход — что и происходит.

**Восстановление автоматическое, а не выбор на экране.** Цена известна и принимается: тот, кто удалял ради чистого старта и передумал в ту же неделю, получит свои данные обратно и должен удалить ещё раз. Экран «Восстановить / Начать заново» можно добавить когда угодно, в схеме он ничего не меняет.

### 17.5. Что остаётся после стирания

Одна строка в `deleted_users`: UID и две даты — когда попросили и когда стёрли. Ни почты, ни номера: держать их после удаления нельзя, а UID нужен, и вот зачем.

`check-phone` **сегодня резолвит номер через Firebase** (`getUIDByPhone`, пункты 14–15 §12 не сделаны), и первичный ключ `users_female` — это тот самый Firebase UID. Значит для телефонного пользователя после полного стирания цепочка такая: вход по номеру → Firebase отдаёт его старый UID → `verify-flash-call` создаёт строку с этим UID → `firebase_import_status` снова `NULL` → **импорт возвращает ровно то, что человек просил удалить**. То же самое делает `/auth/migrate` со старого установленного приложения: `migrateUser` вставляет строку по присланному UID сам, минуя `createFemale`.

Надгробие рвёт эту цепочку в одной точке — **в заявке импорта** (`firebase-import.js`, `claim`): UID, который есть в `deleted_users`, заявку не получает никогда, а `deleted_at IS NULL` там же отсекает аккаунт внутри срока покоя. Одна проверка закрывает все пути сразу, включая тот, который напишут завтра. Маршруты входа (`check-phone`, `verify-flash-call`, `migrate`) читают ту же таблицу отдельно — но не ради данных, а ради ответа: `410 ACCOUNT_DELETED` вместо молча заведённого пустого аккаунта. В `check-phone` проверка стоит **до** `checkRateLimit` и `requestFlashCall`, потому что всё, что ниже, стоит денег и ни при каком исходе не может кончиться входом: регистрации по телефону нет (§11).

Внешнего ключа на `users_female` у `deleted_users` нет и быть не может: надгробие обязано пережить строку, на которую указывает.

Регистрации по почте это не касается вовсе: `createFemale` без `id` генерирует новый случайный UID, Firebase о нём ничего не знает, экспорт возвращает `found: false`. Воскреснуть может только личность, привязанная к старому Firebase UID.

### 17.6. Стирание

`scripts/purge_deleted_accounts.js`, раз в сутки, свой — не внутри `cleanup_expired_data.js`. Тот ежечасно выметает просроченные коды и сожжённые сессии; этот навсегда уничтожает историю человека. Общий лог, общее расписание и общая ветка «одна чистка упала, идём дальше» правильны для первого и неправильны для второго.

Каждый аккаунт — своя транзакция (`purgeOne`):

```sql
DELETE FROM users_female
 WHERE id = $1 AND deleted_at IS NOT NULL AND deleted_at < now() - $2::interval
 RETURNING id, email, deleted_at;      -- 0 строк → ROLLBACK, надгробия нет
INSERT INTO deleted_users (user_id, deleted_at) VALUES ($1, $3) ON CONFLICT DO NOTHING;
DELETE FROM flash_call_sessions WHERE user_id = $1;
DELETE FROM verification_codes  WHERE email   = $2;
```

**Проверка срока повторена внутри `DELETE`, и в ней вся безопасность этого прохода.** Между обходом, который выбрал аккаунт, и этим оператором человек мог войти и снять метку. Строка удаляется, только если она всё ещё помечена и всё ещё просрочена; иначе транзакция откатывается и надгробие не пишется — а написанное, оно отказало бы в импорте живому аккаунту.

Физическую работу делает каскад: `cycles`, `flow_levels`, `comments`, `user_tags`, `day_tags`, `user_devices`, `notification_schedule` уходят вместе со строкой пользователя (`001`, `006`). Два оператора после `DELETE` — для таблиц, у которых ключа в строку пользователя нет: `flash_call_sessions` не несёт внешнего ключа вообще, `verification_codes` привязаны к адресу.

**Потолок на прогон — сто аккаунтов** (`--limit`), и `--dry-run` печатает список, ничего не трогая. Потолок на задании, вся суть которого — необратимое удаление: что бы ни сломалось выше, оно сломается на сотне аккаунтов и попадёт в лог до того, как за ними последуют остальные.

**Прогон, упёршийся в потолок, пишет `WARN`** (`capped` в ответе `purgeDue`). Обход выбирает с `LIMIT`, поэтому `due` никогда не больше потолка, и без этой строки лог одинаков и когда просрочено сто аккаунтов, и когда тысяча. Невыбранные ждут следующих суток, а эти сутки берутся из запаса между сроком покоя и потолком 152-ФЗ (§17.2) — из того самого, ради которого выбраны четырнадцать дней, а не тридцать. Очередь, растущая молча, этот запас и съедает.

### 17.8. Клиент

Настройки → «Удалить аккаунт» → деструктивный лист: что удаляется, дата, после которой это окончательно (сервер возвращает её в `purge_after`), и что вход до неё всё вернёт. Второго подтверждения кодом нет.

По `200` — ровно путь logout (§6): `cancelAll()` наблюдений, `wipe`, `.notAuthenticated`. **При любом исходе запроса**, как и `.logout` после D4: человек попросил уйти — уход должен состояться. Промах не страшен и лечится сам: строки устройства уже нет, следующий прогон вернёт `401`, и выход случится на нём.

При входе с `restored: true` — сообщение о том, что аккаунт восстановлен; отдельного экрана это не требует.

### 17.9. Известные ограничения

**Другие устройства сохранят локальную копию.** Их `device_id` больше нет, следующий прогон — `401`, а §6 на `401` базу не трогает («разлогинили с другого телефона, человек тот же»). Отличить «аккаунт удалён» от «выкинули устройство» на этом пути нечем, и заводить ради этого поле в ответе не стоит того: локальные данные лежат на собственном телефоне человека, а `claimOwner` при следующем входе решит по `user_id`, стирать их или нет.

**Копия в Firebase остаётся до переезда.** `deleted_users` закрывает воскрешение — в наше хранилище удалённые данные не вернутся ни одним из путей (§17.5), — но сами записи v2.0 продолжают лежать у старого оператора.

**Решение: они уходят целиком вместе с переездом на новую площадку, в течение года, отдельными постепенными процедурами.** Ветку удаления в облачной функции ради этого не заводим: она стоила бы правки и проверки в проекте, который целиком выключается, и закрывала бы по одному аккаунту то, что всё равно будет закрыто разом.

Цена названа здесь, а не обнаружена потом: **между стиранием на нашей стороне и переездом копия данных удалившегося человека существует у стороннего оператора.** Наша часть удаления при этом полная и в срок; формулировка в политике конфиденциальности должна описывать именно это, а не обещать, что через четырнадцать дней данных нет нигде.

`deleted_users` — заодно и рабочий список для тех процедур: это ровно те UID, чьи записи в Firebase не переносятся, а уничтожаются. Ещё один довод хранить UID, а не выбрасывать его вместе со строкой.

**Бэкапы хостинга переживают стирание** и раскатываются целиком; поштучно из них ничего не достают. Строка об этом — в политике конфиденциальности, а не в коде.

### 17.10. Отвергнутые варианты

| Что | Почему отвергнуто |
|---|---|
| Код из письма перед удалением | Не останавливает того, у кого телефон в руках, стоит второго эндпоинта и платного звонка для телефонных пользователей, а проверку личности делает не в тот момент — §17.1 |
| Немедленное физическое удаление | Ошибочный тап необратим; в Firebase остаётся копия, которую наш `DELETE` не трогает; и без надгробия следующий вход по номеру возвращает всё обратно |
| Отдельные таблицы-архивы (`deleted_cycles` и т. д.) | Вторая схема из пяти таблиц, которую надо помнить при каждом изменении первой (§4.6). Забыли — потеряли. `deleted_at` даёт то же самое одной колонкой, а работу делает каскад, который уже есть |
| Затирание полей вместо метки (старый `deleteFemale`) | Ничего не удаляет, ломается на `settings NOT NULL`, оставляет устройства живыми и данные на месте — удаление, которого не было |
| Хранить в надгробии номер или адрес | Это ровно те данные, которые просили удалить. Для отказа импорту хватает UID |
| Фильтр `deleted_at IS NULL` по всему пути синхронизации | Не нужен: заявка сносит устройства, и до `/data/sync` удаляемый аккаунт не доживает. Одна проверка в `verifyDevice` закрывает и гонку заявки со входом (§17.3); фильтр, который нужен в одном месте, но написан в десяти, — это девять мест, где его забудут |
| Ветка удаления в облачной функции Firebase, вызываемая при стирании | Проект выключается целиком при переезде в течение года, и его данные уничтожаются отдельными процедурами (§17.9). Править и проверять функцию ради поаккаунтного удаления там, где скоро не станет ни одного аккаунта, — работа, которую отменит собственный срок |
| Пуш другим устройствам о удалении | `401` на ближайшем прогоне говорит то же самое; фоновых пушей 2–3 в час на устройство (§7), и тратить их на это незачем |
| Стирание внутри `cleanup_expired_data.js` | Ежечасное подметание мусора и необратимое уничтожение историй не должны делить лог, расписание и отношение к отказу |
| Срок в 30 дней | Ровно потолок 152-ФЗ: один непрошедший прогон крона — и срок нарушен |

### 17.11. Тесты

`app/test/account-deletion.test.js`, на подставном клиенте, без базы — в той же форме, что `sync-run.test.js` и `firebase-import-run.test.js`. Проверяется не SQL, а решения вокруг него:

1. заявка метит строку и сносит все четыре таблицы сессий в одной транзакции;
2. повторная заявка всё равно подметает устройства (первая могла умереть между `UPDATE` и `DELETE`);
3. неизвестный пользователь — `ROLLBACK` и ни одного `DELETE`;
4. у аккаунта без почты кодов не удаляют;
5. снятие метки отчитывается только тогда, когда метка была;
6. **аккаунт, в который вошли между обходом и удалением, не стирается** — ни строки, ни надгробия;
7. стирание пишет надгробие и добивает две таблицы без ключа;
8. `--dry-run` не открывает транзакции;
9. один упавший аккаунт не останавливает прогон;
10. срок покоя не настраивается выше потолка.

Шестой — главный: у него нет видимого режима отказа. Строка просто исчезнет.

Проверено дополнительно на временном кластере PostgreSQL 18: миграции с нуля до `007`, заявка на живой строке с данными во всех пяти таблицах (данные на месте, сессии сняты), отказ заявки импорта на помеченной строке, отказ стирания до срока, стирание после срока (каскад унёс всё, надгробие осталось) и отказ импорта на строке, пересозданной с тем же UID.

### 17.12. Порядок выкатки

**Миграция `007` применяется до выкатки кода.** `getFemaleByEmail` и `claim` читают `deleted_at`, а `isPurged` — `deleted_users`; против старой схемы это `42703`/`42P01` на каждом входе.

Дальше: код сервера, потом клиент. Между ними сервер уже умеет удалять, но просить об этом некому — эндпоинт закрыт `device_id`, а экрана ещё нет.

Крон ставится в тот же день, что и код, но первым прогоном — `--dry-run`: пока никто не удалялся, ему нечего найти, и это единственный момент, когда в этом можно убедиться заранее.

## 18. Привязка и смена email

**Решение: одна операция «доказать владение адресом и записать его». Коллизия — отказ, слияния аккаунтов нет. Смена открывает окно отката на четырнадцать дней, письмо о ней несёт кнопку возврата.**

| # | Вопрос | Решение |
|---|---|---|
| 1 | Привязка | Опциональная, экран в настройках. Обязательной станет при выводе телефонного входа — §11.5 |
| 2 | Привязка и смена | Один эндпоинт: разница только в том, есть ли кому слать уведомление |
| 3 | Подтверждение нового адреса | Код на него, обязательно и без исключений |
| 4 | Подтверждение старого | Нет. Вместо него — письмо с откатом — §18.6 |
| 5 | Адрес занят | Отказ, с датой освобождения, если держит удаляемый аккаунт — §18.5 |
| 6 | Окно отката | 14 дней; якорь — **первый** адрес цепочки — §18.7 |
| 7 | Страница отката | `api.calendar.red`, серверный HTML, действие по `POST` — §18.8 |
| 8 | Поддержка | Не звено: у неё та же кнопка, что у автомата, и никакой другой — §18.6 |

### 18.1. Принцип

**Ввод кода с адреса — это и есть аутентификация владельца адреса.** Вход по email в этом продукте состоит ровно из этого, и отсюда два следствия, на которых держится вся конструкция:

- **до ввода кода мы не знаем про спрашивающего ничего** и отвечаем осторожно;
- **после ввода кода можно говорить прямо**: услышит только тот, кто держит ящик, а он и так может войти в аккаунт, которому адрес принадлежит.

И второй принцип: **единственный арбитр занятости адреса — `UNIQUE` в момент записи.** Любая проверка до записи — подсказка для экрана, не гарантия. Поэтому «код введён, а адрес занят» — не аномалия, а штатная ветка (§18.4).

### 18.2. Одна операция, два края

Привязка (`email IS NULL`) и смена (`email = A → B`) — одно и то же действие над одной колонкой. Отличий два, и оба на краях:

| | Привязка | Смена |
|---|---|---|
| Уведомление прежнему владельцу | некуда | обязательно |
| Окно отката | не открывается | открывается |

Два эндпоинта дали бы две копии одной валидации с расходящимися ветками. Один эндпоинт, ветка на записи якоря.

### 18.3. Состояние: две таблицы

Заявка и окно живут порознь, потому что у них разный срок и разный смысл: заявка — десять минут до подтверждения, окно — четырнадцать дней после него.

```sql
CREATE TABLE email_change_requests (
    user_id       VARCHAR(50) PRIMARY KEY REFERENCES users_female (id) ON DELETE CASCADE,
    email         VARCHAR(255) NOT NULL,
    code          VARCHAR(6)   NOT NULL,
    expires_at    TIMESTAMPTZ  NOT NULL,
    attempts      INTEGER      NOT NULL DEFAULT 0,
    request_count INTEGER      NOT NULL DEFAULT 1,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE email_revert_windows (
    user_id      VARCHAR(50) PRIMARY KEY REFERENCES users_female (id) ON DELETE CASCADE,
    anchor_email VARCHAR(255) NOT NULL,
    token_sha256 BYTEA        NOT NULL UNIQUE,
    language     VARCHAR(10)  NOT NULL DEFAULT 'en',
    opened_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    expires_at   TIMESTAMPTZ  NOT NULL,
    notified_at  TIMESTAMPTZ
);
```

**Почему не новый `purpose` в `verification_codes`.** Та таблица ключуется адресом, а не пользователем. Два аккаунта, привязывающие один адрес, затирали бы коды друг друга через `ON CONFLICT (email, purpose)`; лимит на пользователя по ней не выражается; внешнего ключа на `users_female` у неё нет и быть не может (§17.3, шаг 5). Здесь всё три раза наоборот.

**`PRIMARY KEY (user_id)` в заявке — не удобство, а правило.** Одна живая заявка на аккаунт: вторая заменяет первую. Это и семантика («передумал, ввожу другой адрес»), и потолок веерной рассылки — один аккаунт не держит двадцать адресов в подтверждении одновременно.

**`PRIMARY KEY (user_id)` в окне — это и есть правило якоря** (§18.7), выраженное `INSERT … ON CONFLICT (user_id) DO UPDATE … WHERE expires_at <= now()`. Пока окно **живо**, новая смена его не открывает, срок не двигает и токена не выпускает. Одна строка кода вместо ветвления, которое иначе пришлось бы помнить.

**Условие на срок в этом `ON CONFLICT` — не оптимизация, а само правило.** Просто `DO NOTHING` отдаёт конфликт любой строке, включая мёртвую: окно истекло, уборка до строки ещё не дошла (а ходит она раз в час), и смена, сделанная в этот промежуток, не открывает окна, не выпускает токена и не шлёт письма — единственная смена во всей функции вообще без защиты. Поэтому просроченная строка перезаписывается целиком: новый якорь, новый токен, `opened_at` заново, `notified_at` обратно в `NULL`. Это ровно то, что §18.7 обещает словами «следующая смена откроет новое окно с новым якорем», и в коде оно должно быть выражено, а не подразумеваться из расписания крона.

**Токен хранится как `sha256`, а не как есть.** Он лежит в письме, то есть уже вне нашего контроля; снимок базы не должен вдобавок отдавать ключи от аккаунтов.

**`notified_at` — крючок для повторной отправки.** Смена уже записана, а Postbox может ответить ошибкой; отказывать в смене из-за недоступной почты нельзя — это выключает функцию вместе с почтовым сервисом. Строка окна уже есть, поэтому ретрай стоит одной колонки: `cleanup_expired_data.js` дотягивает неотправленные.

**Повторная отправка выпускает новый токен.** В таблице лежит дайджест, и первый токен невосстановим по построению — а стоит его замена ничего, потому что ссылка, которую он заменяет, никому не доставлена. Дайджест пишется **до** отправки, иначе ушедшее письмо могло бы нести ссылку, которой в строке уже нет. Попытки прекращаются через сутки: уведомлению, пришедшему на пятый день, защищать почти нечего, а адрес, который почту не принимает, не должен получить три сотни писем за две недели.

**Письмо о повторной смене — обратный порядок: сначала отправка, потом дайджест.** Когда смена уводит адрес с самого якоря (§18.7), якорю уходит то же письмо, а новой ссылки без нового токена не бывает. Но здесь заменяемая ссылка — не «ничья», как у ретрая: она лежит в том же ящике и работает. Записать дайджест первым значило бы погасить её ради письма, которое ещё может не уйти; отправка первой стоит сбоя Postbox ровно этого уведомления и ничего больше.

**Отправка и отметка о ней — две разные неудачи, и в логе они названы по-разному.** Письмо ушло, а `UPDATE notified_at` не прошёл — это не «не удалось уведомить»: уборка прочитает `NULL` как «никому не сказали», выпустит новый токен и пошлёт второе письмо, погасив ссылку в первом. Одно лишнее письмо и требование читать свежее — цена приемлемая, но в логе должно быть видно, что произошло именно это.

**`language` — в окне отката, и только там.** Письмо знает язык из `x-app-language`, а браузер на странице отката приходит без него: без колонки человек, писавший в русском приложении, получит английскую страницу. Заявке он не нужен — письмо с кодом уходит в том же запросе, в котором заголовок пришёл.

### 18.4. Разбор случаев

**Отправка кода** — `POST /auth/email`, `Authorization: Bearer <device_id>`:

| Состояние | Ответ | Почему |
|---|---|---|
| Адрес свободен | `200`, код ушёл | |
| Адрес уже стоит в этой строке | `200 ALREADY_YOURS`, письма нет | Идемпотентность. Письмо ради подтверждения того, что уже верно, — только повод для тревоги |
| Адрес занят живым аккаунтом | `409 EMAIL_TAKEN`, письма нет | §18.5 |
| Адрес занят удаляемым | `409 EMAIL_TAKEN` + `availableAfter` | `isEmailAvailable` уже считает такой адрес занятым (§17.7), и правильно |
| Уже висит заявка на другой адрес | Новая заменяет старую | §18.3 |
| Невалидный формат | `400 INVALID_EMAIL` | Тот же `EmailValidation.validateAndNormalize`, что в `check-email` |
| Аккаунт в сроке покоя | недостижимо | `verifyDevice` фильтрует `deleted_at IS NULL`, устройств у такого аккаунта нет (§17.3) |

**Подтверждение** — `POST /auth/email/confirm`:

| Состояние | Ответ | Почему |
|---|---|---|
| Код верный, адрес свободен | `200`, запись | |
| **Код верный, адрес заняли за эти десять минут** | `409 EMAIL_TAKEN`, заявка цела | Гонка с регистрацией через `check-email`. Человек не виноват, что проиграл её, но и записать нельзя: занявший тоже доказал владение ящиком |
| Код верный, адрес уже наш | `200`, no-op | Двойной тап |
| Смена внутри открытого окна, и покидаемый адрес — **сам якорь** | `200`, окно не двигается, якорю уходит письмо с новой ссылкой | Единственная смена, о которой иначе не узнал бы никто — §18.7 |
| Смена, когда прежнее окно **истекло**, а уборка до строки не дошла | `200`, открывается новое окно с новым якорем | Правило якоря — про живое окно. Мёртвая строка перезаписывается вставкой, иначе смена в этот промежуток остаётся без защиты — §18.3 |
| Заявка теперь на другой адрес | `409 PENDING_ADDRESS_CHANGED` | Со второго устройства запросили адрес C, человек вводит код из письма про B. Отдельный код ошибки — иначе на экране «неверный код» при верном коде |
| Код неверный | `400 INVALID_CODE` + `remainingAttempts` | `VerificationCodeUtil.MAX_ATTEMPTS`, три |
| Три неверных | `429 TOO_MANY_ATTEMPTS` | Заявка сожжена, нужна новая |
| Код истёк | `410 CODE_EXPIRED` | Десять минут, как у логина |
| Заявки нет | `404 TOKEN_NOT_FOUND` | |
| Два устройства подтверждают разом | одно `200`, второе `404` | `FOR UPDATE` на строке заявки |

**Транзакция подтверждения — одна, и код удаляется в ней же:**

```
BEGIN
  SELECT email FROM users_female WHERE id = $1 FOR UPDATE      -- старый адрес и блокировка
  SELECT … FROM email_change_requests WHERE user_id = $1 FOR UPDATE
  проверить код, адрес заявки, срок, попытки
  writeProfile(userId, { email }, { client })                  -- 23505 → EMAIL_TAKEN
  INSERT INTO email_revert_windows …                                   -- только если старый был
    ON CONFLICT (user_id) DO UPDATE … WHERE expires_at <= now()         -- мёртвое окно перезаписывается
  SELECT anchor_email, language, expires_at … AND expires_at > now() FOR UPDATE   -- если INSERT ничего не вернул
  DELETE FROM email_change_requests WHERE user_id = $1
  DELETE FROM verification_codes WHERE email IN (старый, новый)
COMMIT
→ письмо на якорный адрес, после коммита: при открытии окна — с токеном из INSERT,
  при смене прочь от якоря — с новым, записываемым после отправки (§18.3)
```

**Удаление кода внутри транзакции — не мелочь.** Сегодня `verifyCode` удаляет его отдельным оператором до того, как вызывающий что-либо записал: сбой между ними съедает код при незаписанной смене. Здесь этого нет по построению.

**Коды по обоим адресам гасятся** по той же причине, что в §17.3, шаг 5: код на старый адрес после смены не даёт войти в аккаунт (адреса там больше нет) — он заводит **пустой новый**, и человек оказывается в чужом на вид календаре, не понимая, что произошло.

`writeProfile` двигает `data_revision` и `profile_revision` (§4.4), поэтому второе устройство узнаёт новый адрес обычным pull'ом. Запись email из `changes.profile` по-прежнему запрещена — правило личности не меняется.

### 18.5. Занятый адрес

Отказ, и никакого переноса. Три варианта, которые вообще существуют:

1. **Отказ** — адрес остаётся у того, кто его занял;
2. **слияние аккаунтов** — слить две истории циклов с пересекающимися датами, два `data_revision`, два набора устройств и курсоров, решить, чей профиль главный, и всё это необратимо. Отдельная спецификация размером с §4; отвергнуто не по цене реализации, а потому что после слияния не к чему откатиться;
3. **забрать адрес** у живого аккаунта — захват.

За коллизией стоит понятный человек: пользователь v2.0 вошёл по номеру, а когда-то завёл ещё и аккаунт по почте в v3. Два его собственных аккаунта, и ценная история — на телефонном. Поэтому отказ обязан быть действием:

- по умолчанию экран предлагает **другой адрес**;
- кому нужен именно этот — войти в тот аккаунт и удалить его. И тогда `availableAfter`: **удаление освобождает адрес только после стирания** (§17.6), строка живёт до крона и держит `UNIQUE`. Без даты в ответе человек удалит второй аккаунт и упрётся в ту же ошибку, не понимая почему.

**Раскрываем занятость до отправки кода.** Формально это оракул, но такой же оракул уже стоит в `/auth/check-email` и он шире — без аутентификации и с полем `exists`. Прятать здесь — театр, а платит за него живой человек: код, отправленный на адрес, который всё равно нельзя привязать. С одной оговоркой: **неудачная проверка тратит ту же квоту, что отправка** (§18.10), иначе перебор через привязку окажется дешевле перебора через `check-email`, где каждый запрос хотя бы шумит письмом.

### 18.6. Почему уведомление идёт в комплекте с откатом

Модель угрозы у смены почты одна: чужой человек с разблокированным телефоном. Кода из письма против неё нет — по тому же доводу, по которому его нет перед удалением (§17.1).

**Уведомление без отката — худший из вариантов, а не компромисс.** Получив «адрес вашего аккаунта изменён», человек не может войти (его адрес больше не логин) и остаётся с одним действием: написать в поддержку. А там **проверить его нечем**: единственный способ подтверждения личности в этом продукте — код на адрес аккаунта, а адрес аккаунта теперь у того, кто его сменил. То есть такое уведомление гарантированно порождает обращения, которые мы обязаны отклонять.

Проверка «он знает старый адрес и пишет с него» не спасает. Знание старого адреса — не секрет: его знает каждый, кому человек писал письмо, и в нашем сценарии — в первую очередь тот, у кого телефон. Заголовок `From` подделывается. **Асимметрия в направлении: автомат отправляет секрет в ящик, поддержка получает утверждение из ящика.** Первое доказывает владение, второе — знание.

Проверка по деталям аккаунта здесь вообще перевёрнута: телефон в руках у нападающего, он открывает приложение и отвечает на любой вопрос про аккаунт лучше настоящей владелицы.

**Поддержки в схеме нет вовсе, и это решение, а не пропуск.** Ссылка выпускается автоматом и уходит в письме сама; повторную отправку берёт на себя уборка (§18.3), а смену прочь от якоря — сам путь подтверждения (§18.7). Ни одного случая, где оператор нужен, не осталось, и раз так — не надо давать ему и кнопки: социальная инженерия против живого человека это основной способ угона аккаунтов везде, где у оператора есть право что-то вернуть, а единственная надёжная защита от неё — отсутствие такого права. Проверка личности целиком остаётся в доставке письма: автомат отправляет секрет в ящик, и больше никто ничего не отправляет. Обращение «письмо не пришло» закрывается тем же, чем и всегда, — проверить спам и дождаться ретрая; вернуть аккаунт по переписке нельзя, и это не то, что стоит чинить.

**Письмо не содержит слов «обратитесь в поддержку».** Один призыв к действию и ни одного альтернативного пути — иначе часть людей пойдёт писать вместо того, чтобы нажать, и живой человек станет обязательным звеном в ста процентах случаев вместо пяти.

**Кода со старого адреса не требуем.** Почту меняют чаще всего те, кто доступ к старой теряет; такое требование выключает функцию ровно для них.

**Сессии при смене не трогаем.** Смена сделана с аутентифицированного устройства; выкидывать остальные — помогать тому единственному, от кого мы защищаемся. Откат — наоборот, сносит все (§18.8).

### 18.7. Правило якоря

Вопрос «а если сменить адрес три раза подряд» — не крайний случай, а основной путь атаки, если правило выбрано наивно:

- **«каждая смена выпускает токен, новая гасит предыдущий»** — нападающий меняет адрес дважды (`A → B → C`), вторая смена гасит токен, ушедший жертве. Защита выключается двумя тапами;
- **«токены живут параллельно, любой откат гасит цепочку»** — смена `B → C` шлёт токен на B, то есть **самому нападающему**; он открывает свою ссылку, возвращается на свой же B, цепочка гаснет. Защита выключается снова.

Устойчивое правило одно:

> **Окно отката открывает первая смена, и владеет им первый адрес цепочки. Последующие смены внутри окна не выпускают токенов, не двигают якорь и не продлевают срок.**

- якорь — адрес, стоявший на аккаунте в момент открытия окна;
- внутри окна смены проходят молча: **промежуточных писем нет.** Адрес B принадлежит либо тому же человеку, либо нападающему — в обоих случаях письмо туда бесполезно, а второму ещё и сигнал;
- откат возвращает адрес **на якорь**, а не на предыдущее звено;
- окно истекло без отката — цепочка застыла; следующая смена откроет новое окно с новым якорем. **Строку при этом перезаписывает сама вставка, а не уборка** (§18.3): полагаться на то, что крон уже унёс мёртвое окно, значит оставить час, в который смена проходит вовсе без защиты.

Сколько бы смен ни сделал нападающий, он не может ни сжечь токен, ни разбавить его, ни дотянуться до якорного ящика.

**Одно исключение, и называет его покидаемый адрес.** Молчание внутри окна держится на том, что промежуточный адрес принадлежит либо тому же человеку, либо нападающему. Это перестаёт быть верным ровно тогда, когда покидаемый адрес — сам якорь: цепочка `A → B → A` вернулась в начало, вернуть её туда мог только владелец `A`, и следующая смена уводит аккаунт именно с того ящика, ради которого окно и открывали. Оставленная молчаливой, она — единственная смена во всей функции, о которой не узнаёт никто: нового окна не открывается, а ссылка из первого письма истечёт по сроку первой смены, когда бы вторая ни случилась.

Поэтому смена прочь от якоря шлёт якорю то же письмо с новой ссылкой. **Окно при этом не двигается**: тот же якорь, тот же срок, та же строка — меняется только токен. Правилу это не противоречит и лазейкой не становится: чтобы сюда попасть, нужно ввести код, присланный на якорный адрес, — то есть ссылку якоря может погасить только тот, кто читает якорный ящик.

Побочный эффект принимается: человек, сам сменивший `A → B`, а через день `B → C`, откатом вернёт себе A, а не B. Он в аккаунте — сменит ещё раз.

Четырнадцать дней — то же число и по тому же основанию, что в §17.2: срок, за который ошибку успевают заметить, и он же — срок хранения якорного адреса (§18.13).

### 18.8. Страница отката

`GET /email-revert/<token>` и `POST /email-revert/<token>` на `api.calendar.red`, ссылка собирается из `PUBLIC_BASE_URL`. Сайт в схеме не участвует: у механизма, который стоит между человеком и потерей аккаунта, не должно быть внешних частей, которые ломает чужая выкладка.

**Серверный HTML, ни строки JS.** Ссылки из писем открываются во встроенных webview почтовых клиентов; серверный HTML работает во всех одинаково, страница на `fetch` + CORS — почти во всех, а «почти» здесь плохое слово.

**Токен сегментом пути, а не в query.** Часть логов и трекеров разносит путь и query по разным полям, и правило редакции в `logger.js` проще написать на один предсказуемый префикс, чем на параметр.

**`GET` ничего не делает.** Почтовые антивирусы открывают ссылки за получателя; действие только `POST` по кнопке. Кук и сессии на странице нет — секрет и есть токен.

Восемь состояний, ru/en по `language` из строки окна:

1. **ссылка жива** — «Вернуть аккаунт RedCalendar на адрес a•••@x.ru?», кнопка, срок. Адрес **маскированный**: в письме он может стоять целиком — письмо уже в этом ящике, — а URL утекает в историю браузера, лог прокси и скриншот;
2. **ссылка жива, но возвращать нечего** — аккаунт уже стоит на якоре: цепочка вернулась в начало сама. Кнопка та же и делает то же самое, но обещает другое — «выйти на всех устройствах»: адрес не сдвинется, а сеансы закончатся, и здесь это и есть польза. Страница узнаёт об этом одним `JOIN` к аккаунту: окно само по себе на такой вопрос не отвечает;
3. **истекла, использована, или токен прокручен** — «ссылка недействительна», без подробностей о том, что именно случилось, но **с указанием открыть ссылку из самого свежего письма**: прокрутка токена (§18.7) — самый частый способ сюда попасть, и рабочая ссылка в этот момент лежит в том же ящике, парой писем ниже;
4. **якорный адрес занят другим аккаунтом** — отдельный текст: единственный случай, где отказ не про человека. Именно занят: отказ записи разбирается по `error`, как в подтверждении, и всё, что не `'Email already in use'` (второй уникальный столбец §11.4, пропавшая строка), уходит в состояние 8. Сказать человеку «ваш адрес занял кто-то другой», когда у нас просто сломалась запись, — и неправда, и на этой странице испуг;
5. **готово** — «адрес возвращён, откройте приложение и войдите по a•••@x.ru; все устройства вышли»;
6. **сеансы завершены** — то же для состояния 2: менять адрес не понадобилось, устройства вышли;
7. **слишком много запросов** — свой бюджет страницы (§18.10) отвечает страницей, а не стопкой скобок;
8. **наша ошибка** — отдельный текст, и это не педантизм. Состояние 3 в роли обработчика исключений говорит «ссылка недействительна» про ссылку, которая цела и не потрачена, — а человек, однажды это прочитавший, второй раз её не откроет. Восьмое состояние говорит, что сбой наш и открыть стоит ещё раз.

**Транзакция отката:**

```
BEGIN
  SELECT user_id FROM email_revert_windows WHERE token_sha256 = $1          -- без блокировки
  SELECT … FROM users_female WHERE id = $1 FOR UPDATE                       -- аккаунт первым
  SELECT … FROM email_revert_windows
   WHERE user_id = $1 AND token_sha256 = $2 AND expires_at > now() FOR UPDATE
  writeProfile(user_id, { email: anchor_email }, { client })   -- только если адрес не якорный;
                                                               -- 'Email already in use' → состояние 4,
                                                               -- любой другой отказ → состояние 8
  DELETE FROM user_devices        WHERE user_id = $1           -- все сессии
  DELETE FROM flash_call_sessions WHERE user_id = $1
  DELETE FROM email_change_requests WHERE user_id = $1
  DELETE FROM verification_codes  WHERE email IN (якорь, текущий)
  DELETE FROM email_revert_windows WHERE user_id = $1
COMMIT
```

**Порядок блокировок: сначала `users_female`, потом окно** — тот же, что в транзакции подтверждения (§18.4). Естественный порядок здесь обратный, потому что строку называет токен, и он же — взаимная блокировка: подтверждение держит аккаунт и ждёт окно, откат держит окно и ждёт аккаунт, PostgreSQL убивает одну из транзакций с `40P01`. Пара не выдуманная, это и есть сценарий функции: нападающий меняет адрес ещё раз ровно тогда, когда владелец якоря жмёт кнопку. Поэтому первый `SELECT` читает только `user_id` и **не берёт блокировки** — нечего блокировать, кроме имени строки, — а всё, на чём стоит решение (та ли это ссылка, жив ли срок), перечитывается под блокировкой ниже. Заодно это закрывает и гонку с прокруткой токена: ссылка из старого письма к моменту второго чтения строке уже не соответствует и работать перестаёт, как и должна.

**Снос сессий — половина смысла отката.** Без него нападающий остаётся внутри аккаунта и повторит смену назавтра. Он же делает случайное срабатывание безобидным: данные не тронуты, владелец входит обычным кодом. А в состоянии 2 это и весь смысл: адрес уже вернули, писать нечего — но тот, кто его менял, никуда не делся, и ссылка из письма остаётся единственной кнопкой, которая его выкидывает.

**Откат работает и на аккаунте в сроке покоя, и метку не снимает.** Это не недосмотр: цепочка «сменил адрес → удалил аккаунт» иначе не разматывается вовсе. Откат возвращает адрес, вход по нему восстанавливает аккаунт (§17.4) — каждая половина делает свою работу. **Поэтому `requestDeletion` окно не сносит**, хотя рядом сносит всё остальное; заявку на смену — сносит.

### 18.9. Письма

Два новых шаблона, `templates/email/{ru,en}/`:

**`bind` — код.** Отдельный от `verification`, а не переиспользование: нынешний текст говорит «код для подтверждения действия», а человек обязан видеть, **что** подтверждает и **к какому аккаунту** прицепят адрес — «к аккаунту с номером +7•••••••56», «вместо a•••@x.ru». Плюс строка «если это были не вы — просто не вводите код, ничего не произойдёт»: письмо уходит на адрес, который человек мог не запрашивать, и это единственный канал, где мы можем ему это сказать.

**`email-changed` — уведомление с кнопкой.** Что произошло, что будет, если ничего не делать, кнопка, до какого числа она работает, «если меняли вы — делать ничего не нужно». Без картинок, без второй ссылки, тема прямая: доставка этого письма — несущая, оно и есть вся защита.

Оба уходят через Postbox как транзакционные: сообщение об изменении в собственном аккаунте получателя рекламой не является, согласия не требует и **кнопки отписки содержать не должно** — её наличие как раз признак массовой рассылки. Суточная квота Postbox общая с кодами, это стоит проверить до выкатки, а не после.

### 18.10. Лимиты

| Эндпоинт | Бюджет |
|---|---|
| `POST /auth/email` | `sendLimiter` на адрес (§16) **и 5 отправок за 30 минут на пользователя** |
| `POST /auth/email/confirm` | `verifyLimiter` |
| `GET`/`POST /email-revert/<token>` | Отдельный бюджет на адрес, уровня `verifyLimiter` |

**Лимит на пользователя — новый и обязательный.** Привязка открывает канал, которого раньше не было: аутентифицированная рассылка на произвольные адреса. Существующие лимиты его не ловят — они считают на адресат, а здесь каждый адресат новый. Число то же, что у кодов входа (5 за 30 минут, `services/verification.js`), чтобы два похожих потолка не разъехались молча.

`services/rate-limit.js` ключуется по `req.ip`, и параметром ключа здесь не обойтись: кто спрашивает, известно только после проверки токена устройства, то есть уже внутри обработчика, а не в middleware. Поэтому в модуле появился `createCounter` — счётчик, который он заводит и подметает сам, а ключ выбирает вызывающий. Модуль для того и отделён от мест вызова (§16).

Перебор токена смысла не имеет — 32 случайных байта, — бюджет здесь против шума, а не против угадывания.

### 18.12. Клиент

Настройки → «Электронная почта»: у кого адреса нет — «Привязать», у кого есть — показанный адрес и «Изменить». Дальше экран ввода адреса и экран кода — второй уже есть у входа.

Обрабатываются три ответа сверх обычных: `EMAIL_TAKEN` (с `availableAfter`, если он пришёл), `PENDING_ADDRESS_CHANGED`, `ALREADY_YOURS`. После успеха ничего перезагружать не нужно: `writeProfile` двинул `profile_revision`, и адрес приедет ближайшим прогоном.

В ответе подтверждения два флага, и показывать надо второй: `revertWindowOpened` — открылось ли окно, `previousNotified` — ушло ли письмо на прежний адрес. Совпадают они не всегда: смена прочь от якоря письмо шлёт, а окна не открывает (§18.7).

`previousNotified` — про факт, а не про намерение, и на двух путях он считается по-разному. Открытое окно отвечает `true` и при сбое Postbox: строка осталась с `notified_at IS NULL`, уборка письмо дошлёт, и «письмо идёт» остаётся правдой. У смены прочь от якоря ретрая нет (§18.13) — строка уже отмечена отправленной, уборка её не возьмёт, — поэтому там флаг равен исходу этой единственной отправки. Оба поля приходят всегда, в том числе на подтверждении собственного адреса, где оба `false`.

Привязка **опциональная**: экран закрывается, ничего не блокирует. Обязательной она станет отдельным решением при выводе телефонного входа (§11.5), и тогда понадобится признак в ответе `/data/sync` — сейчас его не заводим.

### 18.13. Известные ограничения

**После окна пути назад нет.** Та же сделка, что в §17.2, и по той же причине: дальше держать старый адрес не на чем. Хранение якоря заканчивается вместе с окном — это персональные данные, убранные человеком с аккаунта, и срок у них должен быть назван. Держать дольше «на всякий случай» нельзя ещё и потому, что адреса перевыпускают: корпоративный ящик уходит следующему сотруднику, освободившийся адрес достаётся постороннему, и бессрочный якорь превращается в бессрочный ключ от аккаунта у неизвестно кого.

**У повторного письма ретрая нет.** Уведомление о смене прочь от якоря (§18.7) уходит один раз: строка к этому моменту уже отмечена отправленной, и уборка её не возьмёт — а если бы взяла, перепослать смогла бы только с новым токеном, погасив ссылку, которая в ящике работает. Если Postbox молчал именно в эту минуту, у человека остаётся письмо о первой смене — рабочее, но со своим сроком.

**Срок в письме и на странице — по UTC, и это написано прямо в строке** («до 14.09.2026 (UTC)»). Зону читателя не знает ни письмо, ни страница: письмо читают где угодно, а страница по построению без JS, и браузер о ней не сообщает. Голая дата была бы обещанием, которого мы не держим западнее UTC, — там окно кончается на сутки раньше названного дня. Названная зона стоит пяти символов и верна везде; локализовать её было бы можно только ценой JS на странице, которая существует ровно затем, чтобы работать без него.

**Доставка уведомления не гарантирована.** `notified_at` отвечает за отправку, не за доставку: письмо, попавшее в спам, выключает всю защиту, и узнать об этом мы не можем.

**Слияния аккаунтов нет.** Человек с двумя своими аккаунтами выбирает один — §18.5.

**Адрес удаляемого аккаунта занят до стирания**, то есть до четырнадцати дней. Освободить его досрочно можно было бы, разрешив забрать адрес у аккаунта в сроке покоя — тот, кто ввёл код, владеет ящиком и мог бы в тот аккаунт просто войти. Отложено, а не отвергнуто: цена — у того аккаунта исчезает путь восстановления, то есть мягкое удаление досрочно становится окончательным, и это требует своего деструктивного листа. Готовый выход, если обращения пойдут.

**Откат возвращает на первый адрес цепочки**, а не на предыдущий — §18.7.

**Адреса не нормализуются сверх `lowercase` и `trim`.** `a.b@gmail.com` и `ab@gmail.com` — один ящик у Gmail и два разных адреса у нас. Значит один человек может привязать «второй» адрес того же ящика, и `UNIQUE` этого не заметит. Нормализация по правилам конкретных провайдеров — угадывание чужой политики, которое ломается в день её изменения.

**Пока телефонный вход жив, смена почты не запирает пользователя v2.0**: у него остаётся номер. После §11.5 это перестанет быть верным, и откат станет единственным путём назад — ещё один довод сделать его сейчас, а не тогда.

### 18.14. Отвергнутые варианты

| Что | Почему отвергнуто |
|---|---|
| Слияние аккаунтов при коллизии | Две истории циклов с пересекающимися датами, два `data_revision`, два набора устройств; необратимо. После слияния не к чему откатиться — §18.5 |
| Код со старого адреса | Выключает функцию ровно для тех, кто доступ к старому ящику потерял, — то есть для основного случая |
| Уведомление без отката | Порождает обращения, на которые нельзя безопасно ответить: адрес аккаунта уже у того, кто его сменил — §18.6 |
| Ручной откат поддержкой по письму | Вся проверка сводится к суждению человека о заголовке `From`, а первым в очереди стоит тот, у кого телефон |
| Отложенная смена (вступает в силу через N дней) | Человек не понимает, почему адрес не сменился, а тому, кто теряет доступ к старому ящику сейчас, всё равно приходится ждать |
| Новый `purpose` в `verification_codes` | Ключ по адресу, а не по пользователю: два аккаунта затирают коды друг друга, лимит на пользователя не выражается, внешнего ключа нет — §18.3 |
| Резервирование старого адреса на время окна | Чтобы им завладели, ящик должен быть перевыпущен и зарегистрирован в RedCalendar за две недели. Ветка отказа на странице дешевле индекса и проверки в пути регистрации |
| Страница отката на сайте (Firebase Hosting) | JS + CORS во встроенных webview почтовых клиентов, второй деплой, контракт в двух местах — и всё ради домена, который и так совпадает по второму уровню с адресом отправителя |
| Редирект `calendar.red/e/<token>` → API | Работает и стоит четырёх строк, но добавляет внешнюю часть, которую надо не забыть перенести при переезде сайта с Firebase (§16 «Отключение Firebase»). Ссылка ставится сразу на `api.calendar.red` |
| Выход со всех устройств при смене | Помогает ровно тому, от кого защищаемся: смену сделали с аутентифицированного устройства. При откате — наоборот, обязателен |

### 18.15. Тесты

`app/test/email-binding.test.js`, на подставном клиенте, без базы — в форме `account-deletion.test.js`. Проверяется не SQL, а решения вокруг него:

1. привязка на пустом адресе: профиль записан, окно **не** открыто, письма об изменении нет;
2. смена: профиль записан, окно открыто, якорь — старый адрес, письмо поставлено в очередь;
3. **адрес занят между отправкой и подтверждением** — отказ, заявка цела, профиль не тронут;
4. вторая смена внутри окна: якорь и срок не сдвинулись, второго токена нет;
5. заявка перезаписана вторым адресом — код из первого письма даёт `PENDING_ADDRESS_CHANGED`, а не «неверный код»;
6. три неверных кода сжигают заявку;
7. подтверждение своего же адреса — no-op без письма;
8. откат: адрес вернулся на якорь, все устройства снесены, окно закрыто, коды по обоим адресам сняты;
9. **откат на аккаунте в сроке покоя возвращает адрес и не снимает метку**;
10. откат по истёкшему, повторному и неизвестному токену — ничего не меняет;
11. якорный адрес занят к моменту отката — отказ, окно остаётся открытым до срока;
12. `requestDeletion` сносит заявку и **оставляет окно**;
13. лимит на пользователя считает и неудачную проверку занятости, а не только отправки;
14. **смена прочь от якоря внутри окна** — якорю уходит письмо с новой ссылкой, а якорь, срок и строка не сдвинулись;
15. то же письмо не ушло — токен не заменён, ссылка из первого письма цела;
16. откат на аккаунте, уже стоящем на якоре, — адрес не пишется, устройства снесены, окно закрыто;
17. страница отката видит, что возвращать нечего;
18. **подтверждение своего же адреса отвечает обоими флагами** — `previousNotified` в этой ветке терялся, и до клиента доходил не `false`, а отсутствующий ключ;
19. **откат блокирует аккаунт раньше окна** — тот же порядок, что в подтверждении, и первый `SELECT` блокировки не берёт;
20. окно, закрытое между выборкой уборки и её записью, письма не получает — иначе ссылка в нём не соответствовала бы ни одной строке;
21. **смена после истечения окна открывает новое** — с якорем на покидаемом сейчас адресе, а не с прежним; вставка перезаписывает мёртвую строку целиком;
22. уведомление, которое не удалось отправить, не отмечается как отправленное — `previousNotified` на пути без ретрая равен исходу отправки;
23. отказ записи при откате, не являющийся занятостью адреса, не выдаётся за неё.

Третий и девятый — главные: у обоих нет видимого режима отказа.

`app/test/email-render.test.js` — письма: оба шаблона в обоих языках и обоих форматах загружаются и рендерятся без единого незаполненного `{{…}}`, у каждого письма своя тема, и уведомление о смене несёт ссылку в обеих частях. Молчаливый режим отказа здесь у уведомления: шаблон, потерянный после переименования, роняет путь кода честной 500-й, а путь уведомления — нет, потому что `notify()` глотает ошибку по построению, и защитное письмо просто не уходит.

Отдельно — на временном кластере: миграции с нуля до `008`, полный проход привязка → смена → смена внутри окна → смена прочь от якоря → откат на живой строке с данными, каскад при стирании (обе таблицы уходят сами) и страница отката по HTTP настоящим сервером. Там же воспроизведена и закрыта взаимная блокировка §18.8: до правки пара «подтверждение против отката» давала `40P01`, после — вторая транзакция просто ждёт первую, и двадцать одновременных гонок проходят без единой ошибки.

### 18.16. Порядок выкатки

**Миграция `008` применяется до выкатки кода.** Обе таблицы читаются на первом же запросе привязки, против старой схемы это `42P01`.

Дальше одним куском: сервер (эндпоинты, письма, страница отката) — потом клиент. Между ними сервер уже умеет привязывать, но просить об этом некому: экрана ещё нет, а эндпоинт закрыт `device_id`.

**Страница отката выкатывается не позже письма, которое на неё ссылается** — иначе первая же смена пошлёт человеку ссылку в 404. Практически это одно и то же выкатывание, но порядок внутри него именно такой.

`PUBLIC_BASE_URL` и суточная квота Postbox проверяются до включения, а не после первой смены.
